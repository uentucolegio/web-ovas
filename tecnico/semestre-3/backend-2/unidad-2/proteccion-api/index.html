Protección de la API: tu escudo digital 🛡️

Imagina que tu API es como la recepción de un edificio. Cualquiera puede tocar la puerta, pero no todos pueden entrar, y mucho menos hacer lo que quieran adentro. La protección de una API REST consiste en construir esos filtros: decidir quién puede preguntar, con qué frecuencia, cómo hablar con la base de datos y qué decir cuando algo falla.

En este OVA vas a aprender cuatro escudos esenciales: CORS para controlar quién puede consumir tu API desde un navegador, rate limiting para evitar abusos por exceso de peticiones, consultas parametrizadas para que la base de datos no ejecute código malicioso, y manejo seguro de errores para no regalar pistas a los atacantes.

No se trata de memorizar teoría, sino de tomar decisiones de seguridad con confianza. Vas a jugar con configuraciones, ordenar middlewares, reparar consultas y simular ataques. ¡Prepárate para convertirte en guardián de tus APIs! 🚀

✨ Una API bien protegida no es la que nunca falla, sino la que falla sin contar secretos. Aprende a responder con inteligencia bajo presión. 🔒

Objetivos de aprendizaje 🎯

  • 🧠 Comprender el propósito y el funcionamiento de CORS como mecanismo de control de acceso entre orígenes en una API REST.
  • 💡 Aplicar técnicas de rate limiting para prevenir abusos de consumo y garantizar la disponibilidad del servicio.
  • 🔧 Implementar consultas parametrizadas en el acceso a bases de datos para evitar inyecciones SQL y NoSQL.
  • 🛡️ Diseñar un manejo seguro de errores que oculte información sensible y ofrezca respuestas consistentes a los clientes.

CORS Rate limiting Consultas Errores

Puntos: 0 ⭐

CORS (Cross-Origin Resource Sharing) no es un sistema de autenticación, aunque mucha gente lo confunde con eso. Es un mecanismo del navegador que le pregunta al servidor: "¿me permites leer esta respuesta desde otro origen?". Si el servidor dice que no, el navegador bloquea la lectura del resultado.

💡 Recuerda esto

CORS solo afecta a JavaScript que corre en un navegador. No protege contra llamadas hechas con curl, Postman, Insomnia o scripts servidor-a-servidor. Por eso CORS y autenticación van de la mano, pero nunca son lo mismo.

¿Qué decide el servidor?

  • Access-Control-Allow-Origin: qué dominios pueden leer la respuesta.
  • Access-Control-Allow-Methods: qué métodos HTTP están permitidos.
  • Access-Control-Allow-Headers: qué cabeceras puede enviar el cliente.
  • Access-Control-Allow-Credentials: si se permiten cookies o credenciales.

Ejemplo práctico en Express

const allowedOrigins = ['https://app.ejemplo.com', 'https://admin.ejemplo.com'];

app.use(cors({
  origin: function (origin, callback) {
    if (!origin || allowedOrigins.includes(origin)) {
      callback(null, true);
    } else {
      callback(new Error('No permitido por CORS'));
    }
  },
  credentials: true,
  methods: ['GET', 'POST', 'PUT', 'DELETE'],
  allowedHeaders: ['Content-Type', 'Authorization']
}));

🎮 Misión 1: ¿Permites o bloqueas?

Una petición llega con el origen https://evil.com. Tu lista blanca solo tiene https://app.ejemplo.com. ¿Qué hace el servidor?

El rate limiting es como el semáforo de una autopista: limita cuántos autos (peticiones) pueden pasar en un tiempo determinado. Sin él, un atacante podría intentar adivinar contraseñas a gran velocidad, descargar toda tu base de datos o simplemente tumbar tu servicio con tráfico masivo.

Conceptos clave

Término Significado
Límite Máximo de peticiones permitidas.
Ventana Tiempo en que se cuenta ese límite (por minuto, hora, etc.).
Identificador Cómo reconocer al cliente: IP, API key, id de usuario.
429 Código HTTP de "Too Many Requests".

Configuración con express-rate-limit

const rateLimit = require('express-rate-limit');

const limiter = rateLimit({
  windowMs: 15 * 60 * 1000, // 15 minutos
  max: 100, // máximo 100 peticiones por IP
  message: 'Demasiadas peticiones, intenta más tarde.',
  standardHeaders: true,
  legacyHeaders: false,
});

app.use('/api/', limiter);

La regla de oro para hablar con una base de datos es: nunca confíes en datos que vienen del usuario. Si concatenas una entrada directamente en una consulta SQL, un atacante puede inyectar código y leer, modificar o borrar información.

❌ Código vulnerable

const email = req.body.email;
const query = `SELECT * FROM users WHERE email = '${email}'`;
// Si email es: ' OR '1'='1' --
// la consulta devuelve todos los usuarios

✅ Consulta parametrizada

const result = await db.query(
  'SELECT * FROM users WHERE email = $1',
  [email]
);
// El motor trata el valor como dato, nunca como código

En NoSQL también importa

En MongoDB, si pasas directamente un objeto JSON como filtro, un atacante puede inyectar operadores como { "$gt": "" }. La solución es validar el tipo antes de consultar.

🎮 Misión 3: Repara la consulta

Selecciona la versión segura de esta consulta:

// Entrada: req.body.id
const query = "SELECT * FROM productos WHERE id = " + req.body.id;

Cuando algo falla en tu API, el cliente merece una respuesta clara, pero el atacante no merece información útil. Un error que dice "Column 'password' does not exist" o entrega una traza completa de la base de datos está regalando el plano del edificio.

Principios del manejo seguro

  • Usa un formato consistente: { status, message, code }.
  • No expongas rutas internas, nombres de tablas ni contraseñas.
  • Registra los errores detallados solo en el servidor (logs).
  • Devuelve códigos HTTP adecuados: 400, 401, 403, 404, 429, 500.
  • En producción, oculta el stack trace; en desarrollo, sí puedes mostrarlo.

Middleware de errores en Express

app.use((err, req, res, next) => {
  console.error(err); // detalle completo en logs del servidor

  const status = err.status || 500;
  const message = status === 500 && process.env.NODE_ENV === 'production'
    ? 'Error interno del servidor'
    : err.message;

  res.status(status).json({
    error: {
      status,
      message,
      code: err.code || 'INTERNAL_ERROR'
    }
  });
});
