La frontera segura de una API 🛡️

En una aplicación moderna, las API REST son el principal puente de comunicación entre clientes, apps móviles, servicios web y bases de datos. Cada solicitud trae datos: nombres, correos, identificadores, búsquedas, archivos… y, a veces, sorpresas no deseadas.

Un error común es pensar que si el formulario se ve bonito, los datos que llegan al servidor también son limpios. Spoiler: no siempre. Un atacante puede usar herramientas como Postman o Insomnia para enviar exactamente lo que tú no esperabas. Por eso la verdadera frontera de seguridad no está en la pantalla del usuario, sino en el servidor.

Aquí aprenderás a no confiar ciegamente, a validar antes de aceptar y a sanitizar antes de usar. Será como ponerle un detector de metales a cada dato que entra a tu API.

✨ Cada dato recibido es un desconocido hasta que demuestre ser confiable. Aprende a proteger tu API desde la primera línea de defensa. 🚀

Objetivos de aprendizaje 🎯

  • 🧠 Comprender la importancia de validar y sanitizar la información recibida por una API REST como parte de una estrategia de seguridad.
  • 💡 Aplicar buenas prácticas para prevenir vulnerabilidades ocasionadas por entradas de datos no confiables mediante mecanismos de validación, listas blancas y consultas seguras.
  • 🔧 Integrar procesos de validación y sanitización dentro del flujo de procesamiento de una API REST para mejorar su robustez y confiabilidad.

Insignias: ninguna

Antes de defender una API, conviene saber quién ataca. Los datos maliciosos pueden explotar validaciones deficientes de muchas formas. A continuación verás escenarios reales: lee con atención y adivina qué tipo de ataque intenta colarse.

Escenario 1

Un usuario envía su nombre así: <script>alert('hackeado')</script>. Si se guarda y luego se muestra en la web, el navegador ejecuta el código.

Escenario 2

Un cliente envía como correo: ' OR '1'='1. Si se concatena directo a una consulta SQL, puede devolver todos los usuarios.

Escenario 3

En una API con MongoDB, el cuerpo de la petición envía {"$gt": ""} para un campo de autenticación y logra pasar el filtro.

Escenario 4

Una app permite subir archivos y ejecuta un comando del sistema con el nombre del archivo. El atacante envía: foto.jpg; rm -rf /.

💡 Recuerda: la validación empieza por reconocer el riesgo. Cada ataque aprovecha que confiamos demasiado en los datos recibidos.

Validar es decirle a la API: "antes de usar esto, demuéstrame que cumple las reglas". Las reglas dependen del campo: un correo no puede ser igual que una edad, y un precio no puede ser negativo.

Campo Regla de validación
NombreNo vacío y longitud máxima
CorreoFormato válido
EdadNúmero entero positivo
PrecioValor decimal mayor que cero
EstadoSolo valores previamente definidos

Un dato puede ser válido funcionalmente y aún así peligroso. Imagina un nombre como Juan <script>alert('x')</script>: pasa la validación de "no vacío", pero al mostrarse ejecuta código. Ahí entra la sanitización.

💡 Recuerda: validar y sanitizar no se excluyen. El flujo ideal es validar → sanitizar → usar.

Una API robusta repite el ritual cada vez que recibe datos: verifica, limpia y vuelve a verificar. Si algo falla, rechaza la solicitud con un mensaje claro. Si todo está bien, avanza.
