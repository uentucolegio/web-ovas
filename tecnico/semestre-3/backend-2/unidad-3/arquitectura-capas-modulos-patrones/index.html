Arquitectura backend: ordena tu código antes de que te ordene a ti 🏗️

Toda API empieza pequeña e inocente: un par de rutas, unos archivos, todo funciona de maravilla. 😌 Pero luego la vida pasa: llegan la autenticación, los productos, los pedidos, los pagos... y si cada funcionalidad se agrega "donde quepa", tu proyecto se convierte en un cuarto desordenado donde nadie encuentra nada. 😅

Piensa en una ruta que registra un producto: recibe los datos del cliente, valida el precio, comprueba permisos, consulta la base de datos y arma la respuesta HTTP. Funciona, sí... pero está haciendo demasiadas cosas a la vez. Cuando una regla cambie, tendrás que tocar código que está enredado con otras funciones. 🧶

La arquitectura backend existe para poner orden: no se trata solo de crear carpetas bonitas, sino de marcar límites claros entre los componentes. Las rutas definen los puntos de entrada, los controladores manejan solicitudes y respuestas, los servicios aplican las reglas del negocio y los repositorios se encargan de los datos. 🧱

✨ Aquí aprenderás a separar responsabilidades con una arquitectura por capas, a organizar tu proyecto con módulos y a usar patrones simples como MVC y Repository. ¡Tu API quedará lista para crecer sin colapsar! 🚀

Objetivos de aprendizaje

Objetivo general: Aplicar principios básicos de arquitectura backend mediante la separación de responsabilidades en capas y módulos y el uso de patrones simples para construir proyectos web organizados y mantenibles.

  • 🔍 Identificar problemas derivados de una organización inadecuada del código backend.
  • 🧩 Diferenciar las responsabilidades de rutas, controladores, servicios y repositorios.
  • 📦 Organizar las funcionalidades de una aplicación backend mediante módulos.
  • 🏗️ Aplicar patrones simples de arquitectura en la estructuración de una API REST.

Dato curioso: los desarrolladores pasamos mucho más tiempo leyendo código que escribiéndolo — algunos estudios de la industria hablan de hasta 10 líneas leídas por cada línea nueva. 😳 Por eso un código desordenado no solo "se ve feo": hace que cada cambio cueste más tiempo y más errores.

A ese desgaste acumulado se le llama deuda técnica: cada atajo que tomas hoy ("ya lo organizo después") es un préstamo que cobra intereses mañana. La buena noticia: ordenar temprano es mucho más barato que ordenar tarde. 💸 

// Una ruta que hace de TODO 😬
app.post('/productos', async (req, res) => {
  const { nombre, precio } = req.body;
  if (precio <= 0) {
    return res.status(400).json({ mensaje: 'Datos inválidos' });
  }
  const producto = await guardarProducto(nombre, precio);
  res.status(201).json(producto);
});

Esta ruta mezcla responsabilidades. Haz click en las 3 líneas que NO le corresponden (reglas del negocio y acceso a datos) y luego presiona "Revisar".

Imagina un restaurante 🍽️: el mesero (controlador) toma tu pedido y te trae la comida, pero no cocina. La cocina (servicio) decide cómo preparar el plato según las reglas del chef. Y la despensa (repositorio) guarda los ingredientes. La puerta (ruta) simplemente te dirige al mesero correcto.

En una API REST el viaje es igual de ordenado: cada capa hace una sola cosa y le pasa el trabajo a la siguiente:

Organizar solo por capas funciona al principio, pero cuando tu API tiene usuarios, productos, pedidos y pagos, la carpeta services/ se convierte en un cajón con 40 archivos revueltos. 🗃️

La solución es agrupar por funcionalidad: cada módulo es como un barrio de la ciudad que tiene todo lo que necesita (sus rutas, su controlador, su servicio y su repositorio). Si algo de productos falla, sabes exactamente a qué barrio ir. 🏘️

📁 Por capas (todo revuelto)

src/
├── routes/     (8 archivos)
├── controllers/(8 archivos)
├── services/   (8 archivos)
└── repositories/(8 archivos)

🏘️ Por módulos (todo en su barrio)

src/
└── modules/
    ├── productos/  (4 archivos)
    ├── usuarios/   (4 archivos)
    └── pedidos/    (4 archivos)

Ojo 👀: más estructura no siempre es mejor. Una API con dos operaciones no necesita una ciudad completa. La regla de oro: ¿puede un desarrollador encontrar rápido dónde hacer un cambio? Si la respuesta es sí, tu organización funciona.

Un patrón es una receta probada para un problema que se repite. No es código para copiar: es una idea que ya resolvió el problema miles de veces. Dato para la trivia 🎓: MVC nació en 1979 de la mente de Trygve Reenskaug — ¡es más viejo que la web!

🎭 MVC (Modelo-Vista-Controlador)

Separa datos (modelo), presentación (vista) y coordinación (controlador). En una API REST la "vista" suele ser el JSON que consumes desde React o Angular, y el modelo se apoya en servicios y repositorios.

🗄️ Repository

Separa las reglas del negocio de los detalles de acceso a datos. El servicio dice qué necesita ("búscame el producto") y el repositorio decide cómo obtenerlo (SQL, ORM, lo que sea).

// ❌ Consulta pegada al servicio
const producto = await Producto.findByPk(id);

// ✅ El servicio pide lo que necesita, sin saber el "cómo"
const producto = await productoRepository.buscarPorId(id);

Trabajos de grado recientes (Grisales González, 2023; Suárez López, 2026) muestran estos patrones en sistemas reales. El criterio no es "usar todos los patrones", sino los justos para que tu proyecto sea comprensible y proporcional.
