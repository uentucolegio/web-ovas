Documentación y despliegue: que tu backend hable (y vuele) por ti 📦

Tú conoces tu backend de memoria: sabes qué carpetas tiene, qué comandos lo levantan y qué variables necesita. El problema es que esa información solo existe en tu cabeza 🧠. Si mañana otra persona abre tu repositorio —un compañero, un docente o el tú del futuro— lo único que encontrará es código… y una gran pregunta: ¿y esto cómo se ejecuta? 😅

En este OVA vas a aprender a cerrar ese ciclo. Primero verás por qué la documentación es parte del desarrollo y no una tarea que se hace "si sobra tiempo". Después construirás la pieza estrella de todo repositorio: el archivo README 📖, con su descripción, instalación, configuración y ejecución. También aprenderás a crear la tabla de endpoints que le dice al mundo cómo consumir tu API sin leer tu código 🗺️.

Y el gran final: el despliegue. Mientras desarrollas, tu app vive cómoda en tu computador; pero una entrega técnica exige demostrar que funciona en otro entorno 🚀. Revisaremos dependencias, comandos de inicio y variables de entorno para que tu backend deje de depender de "mi compu" y pueda volar a producción (o a una simulación).

✨ Al terminar, tu proyecto no solo funcionará: cualquiera podrá instalarlo, ejecutarlo y desplegarlo usando únicamente lo que está en el repositorio. 🚀

Objetivos de aprendizaje

  • 🧠 Reconocer la documentación como una parte propia del proceso de desarrollo de un proyecto backend.
  • 📖 Elaborar un archivo README con la información esencial para comprender, instalar, configurar y ejecutar una aplicación.
  • 🗺️ Construir una tabla de documentación de endpoints que describa métodos, rutas, parámetros y respuestas de una API.
  • 🚀 Preparar y ejecutar el despliegue de un backend en un entorno de producción o simulación, verificando su correcto funcionamiento.

Durante el desarrollo de un backend, el programador conoce su estructura, sus comandos y sus configuraciones. Sin embargo, esta información debe quedar registrada para que otras personas puedan utilizar el proyecto. Una estructura básica podría ser:

proyecto/ ├── src/ │ ├── app.js // define la aplicación y sus rutas │ └── server.js // pone el servidor a escuchar ├── package.json // dependencias y comandos ├── .env // valores del entorno (¡no se sube!) └── README.md // la carta de presentación del proyecto

La organización del código permite comprender cómo está construido el sistema, mientras que la documentación explica cómo utilizarlo. Un proyecto correctamente documentado permite:

🧯 Reducir errores de instalación
🤝 Facilitar el trabajo colaborativo
🔧 Mejorar el mantenimiento
⚡ Acelerar la incorporación de otros desarrolladores
📦 Facilitar futuras entregas o despliegues

🔑 La idea central

La documentación no debe considerarse una tarea adicional que se realiza al final, sino una parte propia del desarrollo: se escribe y se actualiza mientras el proyecto crece.

📝 Descripción del proyecto

La descripción debe explicar brevemente la finalidad del sistema:

"API REST para gestionar los productos de una tienda. Permite registrar, consultar, actualizar y eliminar productos."

Este tipo de descripción permite comprender rápidamente el propósito del backend sin necesidad de revisar el código fuente.

⬇️ Instalación

El README también debe explicar qué pasos debe seguir una persona para preparar el proyecto. En una aplicación construida con Node.js, por ejemplo, podría indicarse:

  1. Descargar o clonar el repositorio.
  2. Ingresar al directorio del proyecto.
  3. Instalar las dependencias.
npm install

⚠️ Las instrucciones deben corresponder con el funcionamiento real del proyecto. Una indicación incorrecta puede impedir que otra persona logre ejecutar la aplicación.

⚙️ Configuración

Muchos backends necesitan valores que cambian de acuerdo con el entorno donde se ejecutan. Por ejemplo:

PORT=3000 DB_HOST=localhost DB_NAME=tienda

El README puede explicar cuáles variables se necesitan, pero no debe publicar información sensible como:

🔑 contraseñas 🎟️ tokens 🗝️ claves privadas 🗄️ credenciales reales de bases de datos

▶️ Ejecución

Finalmente, debe indicarse el comando necesario para iniciar la aplicación. Por ejemplo:

npm start

Una documentación adecuada debería permitir que otro desarrollador prepare y ejecute el sistema utilizando únicamente las instrucciones disponibles en el repositorio 🎯.

Un backend normalmente ofrece distintas rutas para consultar, registrar, modificar o eliminar información. Por ejemplo:

app.get('/productos', obtenerProductos); app.get('/productos/:id', obtenerProducto); app.post('/productos', crearProducto);

Aunque estas rutas pueden encontrarse leyendo el código, un usuario de la API no debería necesitar conocer su implementación interna para utilizarla. Por esta razón, resulta conveniente construir una tabla de endpoints:

MétodoRutaDescripción
GET/productosConsultar la lista de productos
GET/productos/:idConsultar un producto por su identificador
POST/productosRegistrar un nuevo producto

Cuando una operación requiere información adicional, también debe documentarse. Por ejemplo, los datos de entrada de POST /productos:

CampoTipoRequeridoDescripción
nombrestringSíNombre del producto
precionumberSíPrecio del producto

Y el cuerpo de una solicitud para crear un producto podría contener:

{ "nombre": "Teclado", "precio": 85000 }

⚠️ La regla de oro

La documentación debe mantenerse sincronizada con el código. Si una ruta cambia, debe actualizarse también en la tabla. Una documentación desactualizada puede ocasionar errores al consumidor de la API.

en tu computador
➡️
🔍 Revisión
deps + comandos + env
➡️
🚀 Despliegue
producción o simulación
➡️
✅ Verificación
¿responde la API?

📦 Dependencias

El proyecto debe tener correctamente registradas las bibliotecas necesarias para funcionar. En Node.js, esta información se administra normalmente desde el archivo package.json.

⌨️ Comando de inicio

Debe existir una instrucción clara para iniciar el servidor. Por ejemplo:

"scripts": { "start": "node src/server.js" }

Esto permite que el entorno donde se despliega la aplicación pueda iniciar el backend mediante un comando conocido.

🌍 Variables de entorno

Los valores que pueden cambiar entre entornos deben evitar estar escritos directamente en el código. Por ejemplo:

const PORT = process.env.PORT || 3000;

De esta manera, la aplicación puede recibir el puerto desde el entorno donde se ejecuta y utilizar un valor predeterminado cuando sea necesario.

También deben revisarse:

  • conexiones a bases de datos;
  • direcciones de servicios externos;
  • credenciales;
  • rutas de archivos;
  • configuraciones específicas del entorno local.

🎯 El objetivo es evitar que el funcionamiento de la aplicación dependa exclusivamente del computador del desarrollador.

Actividades

Tres misiones para dejar tu backend documentado y desplegado. Marca cada paso que completes: la barra de cada misión te muestra tu avance 📈.

📖 Misión 1: Documentación del proyecto

Documentación
  1. Crea un proyecto backend básico utilizando Node.js y Express.
  2. Organiza el proyecto con una estructura de carpetas que incluya el código fuente, las rutas y los archivos de configuración.
  3. Implementa al menos tres endpoints: GET /productos (lista), GET /productos/:id (por identificador) y POST /productos (registrar).
  4. Crea un archivo README.md en la raíz del proyecto.
  5. Documenta en el README la descripción del proyecto, las tecnologías utilizadas, los requisitos, el procedimiento de instalación, la configuración y las instrucciones de ejecución.
  6. Ejecuta el proyecto siguiendo las instrucciones documentadas y comprueba su funcionamiento.

🏅 ¡Misión cumplida! Tu proyecto ya se explica solo.

📝 Producto esperado: proyecto backend básico y funcional, acompañado de un archivo README.md que contenga las instrucciones necesarias para comprender, instalar, configurar y ejecutar la aplicación.

🗺️ Misión 2: Construcción de la tabla de endpoints

Documentación de API
  1. Identifica los tres endpoints implementados en la Misión 1.
  2. Registra el método HTTP y la ruta correspondiente a cada endpoint.
  3. Describe brevemente la función de cada operación.
  4. Identifica los parámetros y datos de entrada requeridos.
  5. Indica los códigos de estado HTTP y las respuestas esperadas.
  6. Incorpora la tabla al archivo README.md.
  7. Verifica que la documentación coincida con el comportamiento real de los endpoints.

🏅 ¡Misión cumplida! Tu API tiene su propio mapa.

📝 Producto esperado: tabla de documentación de los tres endpoints, incorporada al archivo README.md, que incluya métodos HTTP, rutas, descripciones, parámetros, datos de entrada, códigos de estado y respuestas esperadas.

🚀 Misión 3: Despliegue funcional

Despliegue
  1. Revisa las dependencias y el comando de inicio del proyecto construido en la Misión 1.
  2. Identifica y configura las variables de entorno necesarias.
  3. Ejecuta o despliega el backend en un entorno de producción o simulación.
  4. Comprueba que el servidor inicia y responde correctamente.
  5. Realiza pruebas de funcionamiento sobre los tres endpoints implementados, verificando: la consulta del listado de productos (GET), la consulta de un producto específico (GET) y el registro de un nuevo producto (POST).
  6. Compara las respuestas obtenidas con los resultados documentados en la tabla de endpoints.
  7. Registra evidencias de las solicitudes realizadas y las respuestas recibidas.

🏅 ¡Misión cumplida! Tu backend vive fuera de tu compu.

📝 Producto esperado: proyecto backend funcional en un entorno de producción o simulación, acompañado de evidencias de ejecución y verificación de los tres endpoints, mediante capturas de pantalla o registros de solicitudes y respuestas.
