Pruebas de la API: el detector de errores del backend 🕵️

Que tu API "funcione" no significa que esté libre de errores 😅. Una ruta puede responder perfecto cuando recibe datos válidos, pero explotar cuando falta un campo obligatorio; una consulta puede funcionar con registros en la base de datos y comportarse raro cuando no encuentra nada; y un cambio en una parte del proyecto puede romper algo que ayer funcionaba de maravilla.

Por eso probar es parte del trabajo diario de quien desarrolla backend. No se trata solo de encontrar bugs, sino de comprobar de forma organizada que el software hace lo que promete. En este OVA vas a aprender a probar endpoints de dos maneras: manualmente, enviando solicitudes tú mismo con herramientas como Postman 🖱️, y automatizadas, convirtiendo tus verificaciones en código que se repite solo con npm test 🤖.

Usaremos como ejemplo una API de productos: GET /productos para consultar y POST /productos para crear. ¿El plan? Probar el camino feliz... y también provocar errores a propósito para ver cómo responde la API. 😈

✨ Al terminar, no dirás "creo que funciona": dirás "lo comprobé" — y tendrás las pruebas para respaldarlo. 🚀

Objetivos de aprendizaje

  • 🧠 Reconocer la importancia de las pruebas como parte del proceso de desarrollo de una API.
  • 🖱️ Ejecutar pruebas manuales sobre endpoints mediante herramientas especializadas.
  • 🗺️ Diseñar casos de prueba que contemplen respuestas exitosas y situaciones de error.
  • 🤖 Implementar pruebas automatizadas básicas para verificar el comportamiento esperado de los endpoints de una API.

Probar una API no es verificar que una ruta responde: es comprobar comportamientos. Cuando envías POST /productos con un nombre y un precio y todo sale bien, solo comprobaste un escenario. Quedan preguntas sin responder:

😶 ¿Y si no se envía el nombre?
🔤 ¿Y si el precio llega como texto?
🚩 ¿Devuelve el código HTTP correcto cuando hay error?
💥 ¿Qué pasa si alguien modifica el controlador después?

🔑 La pieza clave: el caso de prueba

Un caso de prueba es una situación específica que quieres comprobar. Cada uno define una entrada (los datos que envías) y un resultado esperado (lo que debería pasar). Así la prueba deja de ser improvisada y se vuelve un procedimiento verificable.

💡 Dato que motiva: en la industria, un error encontrado cuando el software ya está en producción puede costar muchas veces más caro que detectarlo mientras desarrollas. Probar temprano es literalmente ahorrar tiempo (y sustos) 💸.

Las pruebas manuales son geniales para explorar... pero repetirlas después de cada cambio cansa 😩. Una prueba automatizada convierte la verificación en código: la escribes una vez y la ejecutas mil veces con npm test.

🧰 El combo que usaremos (Node.js + Express):

  • Node.js Test Runner (node:test): el ejecutor de pruebas que ya viene dentro de Node. Cero instalación 🎉.
  • Supertest: biblioteca que hace solicitudes HTTP directo sobre tu app Express, sin levantar el servidor.

📁 La estructura clave:

proyecto/ ├── src/ │ ├── app.js // crea la app Express (sin listen) │ └── server.js // solo la pone a escuchar ├── tests/ │ └── productos.test.js // aquí viven las pruebas └── package.json // "test": "node --test"

Separar app.js de server.js permite que las pruebas importen la aplicación sin ejecutar app.listen() ni ocupar un puerto.

🧪 Así se ve una prueba real:

import test from "node:test"; import assert from "node:assert/strict"; import request from "supertest"; import app from "../src/app.js"; // Dado → Cuando → Entonces (preparar, actuar, verificar) test("GET /productos devuelve 200", async () => { const respuesta = await request(app).get("/productos"); assert.equal(respuesta.status, 200); assert.ok(Array.isArray(respuesta.body)); });

🎯 Pregunta rápida: ¿qué línea del código compara el resultado con lo esperado?

El error clásico del principiante: probar solo lo que sale bien. Una API confiable también responde bien cuando recibe lo que no puede procesar. Para GET /productos/:id:

😊 Caso exitoso

Envías el id de un producto existente → esperas 200 y los datos del producto.

😈 Caso de error

Envías un id que no existe → esperas 404 y un mensaje que lo indique.

❓ Las 4 preguntas de todo buen caso de prueba:

  1. ¿Qué entrada se utilizará?
  2. ¿Qué comportamiento se espera?
  3. ¿Qué código HTTP debería producirse?
  4. ¿Qué información debería contener la respuesta?

🧭 Y en la práctica, el flujo profesional combina ambos mundos: primero exploras manualmente (Postman) para entender el comportamiento, y después conviertes los casos más importantes en pruebas automatizadas que vigilan que nada se rompa con los cambios. Manual explora, automática vigila 🛡️.

🕵️ Misión 1: Comprobación manual de endpoints

Práctica manual

Objetivo: ejecutar pruebas manuales sobre una API REST e interpretar sus respuestas.

  1. Selecciona una API desarrollada durante el curso.
  2. Identifica tres endpoints disponibles.
  3. Ejecuta una solicitud correcta sobre cada endpoint con Postman (u otra herramienta equivalente).
  4. Registra el método HTTP, la ruta, los datos enviados y el código de estado recibido.
  5. Ejecuta al menos una solicitud incorrecta sobre uno de los endpoints.
  6. Explica si la respuesta obtenida corresponde con el comportamiento esperado.

🏅 ¡Misión cumplida! Tus evidencias cuentan la historia completa.

📝 Producto esperado: documento con la evidencia de cuatro solicitudes realizadas, incluyendo capturas de las respuestas y una explicación breve de los resultados obtenidos.

🗺️ Misión 2: Diseño de casos de prueba

Diseño

Objetivo: establecer casos de prueba para verificar diferentes comportamientos de una API.

  1. Selecciona un endpoint de creación, consulta, actualización o eliminación.
  2. Define un escenario exitoso.
  3. Define dos escenarios de error.
  4. Para cada escenario indica los datos de entrada, el resultado esperado y el código HTTP esperado.
  5. Ejecuta manualmente los tres casos y compara los resultados reales con los esperados.

🏅 ¡Misión cumplida! Diseñaste casos con propósito, no pruebas al azar.

📝 Producto esperado: tabla de casos de prueba acompañada de las evidencias de ejecución y una conclusión sobre el comportamiento del endpoint.

🤖 Misión 3: Automatización de una prueba básica

Automatización

Objetivo: implementar una prueba automatizada básica sobre un endpoint existente.

  1. Selecciona uno de los casos verificados en la misión anterior.
  2. Configura una herramienta de pruebas compatible con el proyecto backend (Node.js Test Runner + Supertest).
  3. Implementa una prueba que realice la solicitud correspondiente.
  4. Establece al menos una expectativa sobre el código de estado.
  5. Ejecuta la prueba y comprueba su resultado.
  6. Modifica temporalmente una condición para provocar un fallo y observa cómo la herramienta lo reporta.
  7. Restablece el comportamiento correcto y ejecuta nuevamente la prueba.

🏅 ¡Misión cumplida! Tu primera prueba automatizada está viva.

📝 Producto esperado: fragmento del código de la prueba automatizada, acompañado de evidencia de una ejecución exitosa y una breve explicación de lo observado cuando la prueba falló.
