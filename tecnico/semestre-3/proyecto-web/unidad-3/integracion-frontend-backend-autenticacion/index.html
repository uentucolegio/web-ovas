🔗 Es hora de unir las dos mitades de tu proyecto

Hasta ahora tu proyecto web ha vivido en dos mundos separados. Por un lado está el frontend: las pantallas con HTML, CSS y JavaScript que construiste en la Unidad 2, capaces de validar formularios y consumir APIs públicas. Por el otro está el backend que tu equipo viene desarrollando en esta unidad: la lógica de negocio, la base de datos y los servicios que exponen la información del proyecto. En este tema vas a conectar esas dos mitades para que funcionen como una sola aplicación.

¿Qué significa que el frontend "hable" con tu propia API? Que cuando el usuario abre la página, el navegador ya no muestra datos inventados ni simulados: hace una petición HTTP a un servicio construido por tu equipo, el backend consulta la base de datos y devuelve una respuesta en JSON que el frontend convierte en tarjetas, tablas o listas reales. Y cuando el usuario llena un formulario, esos datos viajan al servidor y quedan guardados de verdad.

Pero conectar no es solo mostrar datos. Una aplicación real necesita saber quién la usa (autenticación), decidir qué puede hacer cada persona (autorización) y responder con claridad cuando algo sale mal (manejo de errores). En esta guía, que corresponde al Tema 2 de la Unidad 3, trabajarás la integración frontend–backend con fetch, el flujo básico de login con token, los roles de usuario y administrador, los códigos de estado HTTP en la práctica y los criterios mínimos de seguridad que todo proyecto debe cumplir.

Todo lo que veas aquí lo aplicarás directamente en el proyecto integrador de tu equipo: al terminar, tu frontend deberá listar y crear registros usando tu propia API, proteger al menos una funcionalidad con login y mostrar mensajes de error útiles cuando el servidor responda con un problema. Ese es el corazón del resultado de aprendizaje de esta unidad. 🔗

✨ Cuando tu formulario guarde un registro en tu propia base de datos y tu página lo muestre al recargar, habrás cruzado la línea que separa una maqueta de una aplicación web real. 🚀

En la Unidad 2 consumiste APIs públicas de internet. La diferencia ahora es que la API es tuya: la construyó tu equipo y expone los datos del proyecto. El mecanismo es el mismo fetch que ya conoces, pero apuntando a las rutas de tu backend, por ejemplo /api/productos.

El ciclo petición–respuesta siempre sigue estos pasos: el navegador envía una petición HTTP → el backend la recibe, ejecuta la lógica de negocio y consulta la base de datos → el backend responde con JSON y un código de estado → el frontend convierte ese JSON en elementos del DOM.

📥 GET: listar registros de tu API

// Listar los productos que guarda tu backend
async function cargarProductos() {
  const respuesta = await fetch('/api/productos');
  const productos = await respuesta.json();
  const lista = document.getElementById('lista-productos');
  lista.innerHTML = productos
    .map(p => `<li>${p.nombre} — $${p.precio}</li>`)
    .join('');
}

📤 POST: crear un registro enviando JSON

// Enviar los datos del formulario al backend
const nuevo = { nombre: 'Camiseta', precio: 45000 };
const respuesta = await fetch('/api/productos', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify(nuevo)
});
if (respuesta.ok) {
  mostrarMensaje('✅ Producto guardado correctamente');
  cargarProductos(); // refresca la lista con el dato nuevo
}

Observa los tres ingredientes del POST: el method, el header Content-Type: application/json (le dice al backend en qué formato viaja el cuerpo) y el body convertido a texto con JSON.stringify(). Al final, el frontend renderiza el resultado en el DOM: la aplicación se siente viva porque lo que se guarda, se ve.

🎯 Mini reto (+5 pts): ¿qué header le indica al backend que el cuerpo de la petición viene en formato JSON?

Son dos preguntas distintas que suelen confundirse. La autenticación responde "¿quién eres?": verifica la identidad del usuario, normalmente con correo y contraseña. La autorización responde "¿qué puedes hacer?": decide si ese usuario, ya identificado, tiene permiso para una acción concreta.

Piensa en un concierto 🎫: mostrar tu cédula en la entrada es autenticación (demuestras quién eres); la pulsera VIP que te deja o no pasar al backstage es autorización (define hasta dónde llegas).

🔑 Flujo básico de login con token

  1. El usuario escribe correo y contraseña en el formulario de login.
  2. El frontend envía esos datos con POST /login (cuerpo en JSON).
  3. El backend verifica las credenciales contra la base de datos.
  4. Si son correctas, el backend genera y devuelve un token: una credencial temporal (la idea detrás de las sesiones y de los JWT) que representa "este usuario ya inició sesión".
  5. El frontend guarda el token y lo adjunta en cada petición siguiente, en el header Authorization.
  6. Las rutas protegidas del backend revisan el token antes de responder: sin token válido, no hay datos.

👥 Roles: usuario y administrador

En un proyecto típico bastan dos roles. El usuario puede ver el catálogo, registrarse y crear sus propios registros. El administrador puede además editar o eliminar cualquier registro y gestionar a los demás usuarios. El backend guarda el rol junto con la cuenta y lo consulta en cada ruta protegida: la interfaz puede ocultar un botón, pero la decisión final de permitir o negar la acción siempre la toma el servidor.

🎯 Mini reto (+5 pts): un usuario con sesión iniciada intenta eliminar un producto y el sistema se lo niega porque su rol no lo permite. ¿Qué mecanismo actuó?

Cuando frontend y backend conversan, las cosas fallan: datos incompletos, sesiones vencidas, rutas equivocadas, errores del servidor. El backend comunica qué pasó con códigos de estado HTTP. Estos cinco aparecerán una y otra vez en tu proyecto:

400 Bad Request — la petición está mal formada o faltan datos: el formulario envió un campo vacío o un JSON inválido.
401 Unauthorized — no estás autenticado: falta el token o ya venció. Toca iniciar sesión de nuevo.
403 Forbidden — estás autenticado, pero tu rol no tiene permiso para esta acción.
404 Not Found — el recurso o la ruta no existe: revisa la URL o el id que pediste.
500 Internal Server Error — el error ocurrió dentro del backend (una excepción, la base de datos caída). El usuario no tiene la culpa: hay que revisar los logs del servidor.

🧯 try/catch + respuesta.ok en la práctica

async function cargarProductos() {
  try {
    const respuesta = await fetch('/api/productos');
    if (!respuesta.ok) {
      // fetch NO lanza error con 404 o 500: hay que revisarlo
      throw new Error('El servidor respondió ' + respuesta.status);
    }
    const datos = await respuesta.json();
    renderizarLista(datos);
  } catch (error) {
    // Aquí caen los fallos de red y el throw de arriba
    mostrarMensaje('⚠️ No pudimos cargar los productos. Intenta de nuevo.');
    console.error(error); // el detalle técnico va a la consola, no al usuario
  }
}

Dos reglas de oro. Primera: los mensajes al usuario deben decir qué pasó y qué hacer ("Tu sesión venció, inicia sesión de nuevo"), nunca jerga técnica como "Error 500 undefined". Segunda: la validación va en ambos lados — el frontend valida para dar respuesta inmediata y buena experiencia, y el backend vuelve a validar todo, porque cualquiera puede saltarse el formulario y enviar la petición directamente.

🎯 Mini reto (+5 pts): tu API respondió con estado 404, pero el catch no se ejecutó y la página intentó renderizar igual. ¿Qué faltó en el código?

No necesitas ser experto en ciberseguridad para proteger tu proyecto, pero sí cumplir tres criterios mínimos que se evalúan en esta unidad:

  • 🔒 Nunca guardes contraseñas en texto plano. En la base de datos solo se almacena el hash de la contraseña (con funciones como bcrypt). Al hacer login, el backend compara hashes: si alguien roba la base de datos, no obtiene las contraseñas reales.
  • 🙅 No confíes en el cliente. Todo lo que llega del navegador puede haber sido manipulado: con las herramientas de desarrollo cualquiera cambia el HTML, se salta tus validaciones o inventa peticiones. Por eso el backend valida los datos y verifica los permisos siempre, aunque el frontend ya lo haya hecho.
  • 🔐 Usa HTTPS en producción. Con HTTP plano, las contraseñas y los tokens viajan legibles por la red. HTTPS cifra la comunicación entre navegador y servidor; las plataformas de despliegue actuales lo ofrecen sin costo.

Un extra que te ahorrará sustos: nunca escribas llaves secretas ni credenciales de la base de datos en el código del frontend, porque todo lo que llega al navegador es público. Los secretos viven en el backend, en variables de entorno.
