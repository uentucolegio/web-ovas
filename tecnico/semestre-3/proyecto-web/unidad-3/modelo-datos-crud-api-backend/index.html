🗄️ Del prototipo al backend: donde viven los datos

En la Unidad 2 tu equipo construyó el frontend del proyecto web: pantallas maquetadas con HTML5 y CSS, formularios validados con JavaScript y hasta un primer consumo simple de datos. Sin embargo, hay algo que ese prototipo todavía no puede hacer: recordar. Si un usuario registra un pedido y recarga la página, todo desaparece, porque los datos solo existían en la memoria del navegador.

Esa es exactamente la carencia que resuelve la capa de backend: un programa que corre en el servidor, guarda la información en una base de datos y la expone al frontend a través de una API. Con esta guía inicias la Unidad 3, dedicada al backend, la integración, las pruebas y el despliegue del proyecto web.

Este primer tema recorre el camino completo de los datos: primero diseñarás el modelo de datos (qué entidades existen en tu proyecto y cómo se relacionan), luego lo convertirás en tablas de una base de datos con sus operaciones CRUD (crear, leer, actualizar y eliminar), y finalmente construirás la API/backend con sus rutas y controladores, para que el frontend que ya tienes pueda pedir y enviar datos reales.

Como hilo conductor usaremos un ejemplo cercano: una app de gestión de pedidos para una tienda de barrio, con usuarios que hacen pedidos de productos. El mismo razonamiento aplica al proyecto de tu equipo, sea cual sea su temática 🛒.

✨ Al terminar este OVA sabrás dibujar el mapa de los datos de tu proyecto, traducirlo a tablas con SQL y diseñar las rutas de la API que conectarán tu frontend con una base de datos real. 🚀

Objetivos de aprendizaje

  • 🧩 Diseñar el modelo de datos del proyecto web identificando entidades, atributos y relaciones a partir de las necesidades reales de la aplicación.
  • 🗄️ Implementar la base de datos del proyecto traduciendo el modelo a tablas con claves primarias y foráneas, y aplicar las cuatro operaciones CRUD mediante sentencias SQL.
  • 🔌 Desarrollar los servicios del backend definiendo rutas REST y controladores que conecten las peticiones HTTP del frontend con las operaciones sobre la base de datos.
  • 🛡️ Aplicar buenas prácticas básicas en el diseño de la API: nombres coherentes de rutas y tablas, y uso correcto de los códigos de estado HTTP en las respuestas.

Antes de escribir una sola línea de SQL o de backend, hay que responder una pregunta: ¿qué información necesita guardar tu aplicación? La respuesta se organiza en un modelo de datos, un plano que describe las entidades (las "cosas" del sistema), sus atributos (los datos de cada cosa) y las relaciones entre ellas.

Pensemos en nuestra app de pedidos de la tienda. Con solo describir el negocio ("los usuarios hacen pedidos de productos") ya aparecen las entidades principales. El modelo quedaría así:

Entidad Atributos principales Se relaciona con…
Usuario id, nombre, correo, contraseña, rol Un usuario realiza muchos pedidos (1:N)
Producto id, nombre, precio, stock Un producto aparece en muchos pedidos, y un pedido tiene muchos productos (N:M)
Pedido id, usuario_id, fecha, estado, total Pertenece a un usuario; se detalla en Detalle de pedido
Detalle de pedido id, pedido_id, producto_id, cantidad, subtotal Entidad intermedia que convierte la relación N:M en dos relaciones 1:N

Este mismo cuadro, dibujado con cajas y líneas, es lo que conocerás como diagrama entidad–relación (ER): cada entidad es una caja con sus atributos, y cada línea indica el tipo de relación (1:1, 1:N o N:M).

Cuando el modelo está claro, traducirlo a una base de datos relacional es casi mecánico: cada entidad se convierte en una tabla, cada atributo en una columna, el identificador se declara como clave primaria (PRIMARY KEY) y cada relación se materializa con una clave foránea (FOREIGN KEY) que apunta a la tabla relacionada. Así se crea la tabla de productos: 

CREATE TABLE productos (
  id     INT AUTO_INCREMENT PRIMARY KEY,
  nombre VARCHAR(100) NOT NULL,
  precio DECIMAL(10,2) NOT NULL,
  stock  INT DEFAULT 0
);

CREATE TABLE pedidos (
  id         INT AUTO_INCREMENT PRIMARY KEY,
  usuario_id INT NOT NULL,
  fecha      DATE NOT NULL,
  estado     VARCHAR(20) DEFAULT 'pendiente',
  FOREIGN KEY (usuario_id) REFERENCES usuarios(id)
);

Sobre esas tablas, toda aplicación repite una y otra vez las mismas cuatro operaciones, conocidas como CRUD por sus siglas en inglés: Create (crear), Read (leer), Update (actualizar) y Delete (eliminar). En SQL, cada una tiene su sentencia:

Operación CRUD Sentencia SQL de ejemplo (tabla productos)
Create — crear INSERT INTO productos (nombre, precio, stock) VALUES ('Café tostado 500 g', 18000, 25);
Read — leer SELECT id, nombre, precio FROM productos WHERE stock > 0;
Update — actualizar UPDATE productos SET precio = 19500 WHERE id = 3;
Delete — eliminar DELETE FROM productos WHERE id = 3;

Ojo con UPDATE y DELETE: si olvidas el WHERE, la sentencia afecta TODAS las filas de la tabla. Es uno de los errores más costosos en bases de datos reales.

El frontend no habla SQL ni toca la base de datos directamente: le pide los datos al backend a través de una API REST, un conjunto de rutas (URLs) que representan recursos y responden en formato JSON. Lo elegante de REST es que las cuatro operaciones CRUD se corresponden con los métodos HTTP que ya conoces de la Unidad 2:

Método + ruta Operación CRUD Qué hace
GET /api/productos Read Devuelve la lista de productos
GET /api/productos/3 Read Devuelve solo el producto con id 3
POST /api/productos Create Crea un producto con los datos que llegan en el cuerpo de la petición
PUT /api/productos/3 Update Actualiza el producto con id 3
DELETE /api/productos/3 Delete Elimina el producto con id 3

Dentro del backend, cada ruta delega el trabajo en un controlador: una función que recibe la petición, ejecuta la consulta en la base de datos y devuelve la respuesta. Así se ve el flujo completo ruta → controlador → base de datos en un backend estilo Express (Node.js); en PHP u otro lenguaje la estructura es equivalente: 

// rutas.js — la ruta conecta URL + método con su controlador
app.get('/api/productos', obtenerProductos);
app.post('/api/productos', crearProducto);

// controladores.js — el controlador habla con la base de datos
async function obtenerProductos(req, res) {
  try {
    const filas = await bd.consultar('SELECT * FROM productos');
    res.status(200).json(filas);            // 200 OK + datos en JSON
  } catch (error) {
    res.status(500).json({ mensaje: 'Error en el servidor' });
  }
}

async function crearProducto(req, res) {
  const { nombre, precio, stock } = req.body; // datos enviados por el frontend
  await bd.consultar(
    'INSERT INTO productos (nombre, precio, stock) VALUES (?, ?, ?)',
    [nombre, precio, stock]
  );
  res.status(201).json({ mensaje: 'Producto creado' }); // 201 Created
}

Fíjate en los signos ? del INSERT: son consultas parametrizadas, un criterio básico de seguridad que evita que un usuario malicioso inyecte SQL a través del formulario.

Un backend bien construido se nota en los detalles. Dos hábitos marcan la diferencia desde el primer día: nombrar con coherencia y responder con el código de estado correcto.

  • Nombres: tablas y rutas en minúsculas, en plural y sin tildes ni espacios (productos, /api/pedidos). Columnas descriptivas y consistentes (usuario_id, no idUsr en una tabla y id_usuario en otra).
  • Rutas por recurso, no por acción: el método HTTP ya dice qué se hace. Es mejor DELETE /api/pedidos/9 que GET /api/borrarPedido?id=9.
  • Códigos de estado: el número de la respuesta le informa al frontend qué pasó, sin tener que adivinar leyendo el mensaje.
Código Significado Cuándo usarlo en tu API
200 OK Todo salió bien Un GET, PUT o DELETE que se ejecutó correctamente
201 Created Recurso creado Un POST que insertó un nuevo registro
404 Not Found No existe Se pidió /api/productos/999 y ese id no está en la base de datos
500 Internal Server Error Falla del servidor La consulta falló, la base de datos no responde o hay un error de código
