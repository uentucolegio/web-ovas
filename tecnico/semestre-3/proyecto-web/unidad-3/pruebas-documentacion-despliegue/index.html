🏁 La última milla: probar, documentar y publicar tu proyecto

Tu proyecto web ya tiene frontend, backend y base de datos funcionando juntos. Sin embargo, un proyecto que "funciona en mi computador" todavía no está terminado. Falta la última milla: comprobar con pruebas que todo hace lo que debe hacer, escribir la documentación que permitirá a otras personas entenderlo y usarlo, y publicarlo en un servidor real para que cualquiera pueda acceder desde internet.

Esta guía corresponde al Tema 3 de la Unidad 3: Pruebas, documentación técnica, manual de usuario y despliegue. Aquí aprenderás a diseñar casos de prueba para los flujos principales de tu aplicación (formularios, casos de uso y operaciones CRUD completas), a redactar un README claro y un manual de usuario, y a preparar el entorno para desplegar tu solución con servicios gratuitos como GitHub Pages, Render o Railway.

Este cierre no es un trámite: en la industria del software, las pruebas evitan que los errores lleguen al usuario, la documentación hace que un proyecto sobreviva a su autor y el despliegue es lo que convierte el código en un producto real. Con este tema completas la evidencia final del curso: aplicación web completa desplegada, código fuente documentado y presentación final.

✨ Un proyecto probado, documentado y publicado en internet deja de ser una tarea de clase y se convierte en tu primera pieza de portafolio profesional. 🚀

Objetivos de aprendizaje

  • 🧪 Diseñar y ejecutar pruebas funcionales y de integración sobre los casos de uso, formularios y flujos CRUD del proyecto web, registrando cada caso de prueba con sus pasos y resultados.
  • 📄 Elaborar la documentación técnica del proyecto, incluyendo un README completo (descripción, requisitos, instalación, uso y estructura) y comentarios útiles en el código fuente.
  • 📘 Distinguir el manual de usuario de la documentación técnica y redactar un manual claro, orientado al usuario final de la aplicación.
  • 🚀 Desplegar la solución en un entorno de producción gratuito, preparando variables de entorno y dependencias, y verificando la publicación con una lista de chequeo.

Probar no es "hacer clic a ver si abre". Una prueba funcional verifica que cada funcionalidad haga exactamente lo que se espera, vista desde el usuario: que el formulario de registro rechace un correo inválido, que el botón "Guardar" realmente guarde, que el mensaje de error aparezca cuando debe. Una prueba de integración va más allá: comprueba que las piezas trabajen juntas, por ejemplo que lo que el usuario escribe en el frontend llegue al backend, se guarde en la base de datos y vuelva a aparecer en el listado.

¿Qué probar en tu proyecto integrador?

  • Casos de uso principales: las acciones que definen tu aplicación (registrar una reserva, publicar un producto, consultar una cita…).
  • Formularios: con datos válidos y con datos inválidos (campos vacíos, correos mal escritos, textos demasiado largos).
  • Flujos CRUD completos: crear un registro, verlo en el listado, editarlo y eliminarlo, confirmando en cada paso que la base de datos quedó como debía.
  • Mensajes al usuario: que los avisos de éxito, error y carga aparezcan en el momento correcto.

Para que las pruebas sean repetibles y no dependan de la memoria de nadie, se documentan como casos de prueba. Cada caso registra un identificador, el escenario que se prueba, los pasos para reproducirlo, el resultado esperado y el resultado obtenido. Así se ve un caso de prueba aplicado a un proyecto de reservas:

ID Escenario Pasos Resultado esperado Resultado obtenido Estado
CP-01 Crear reserva con datos válidos 1. Iniciar sesión. 2. Ir a "Nueva reserva". 3. Llenar todos los campos. 4. Clic en "Guardar". Mensaje de éxito y la reserva aparece en el listado Mensaje de éxito y reserva visible en el listado ✅ Pasa
CP-02 Crear reserva con correo inválido 1. Ir a "Nueva reserva". 2. Escribir "juan@" en el correo. 3. Clic en "Guardar". Mensaje de error y la reserva NO se guarda La reserva se guardó con el correo incompleto ❌ Falla

El caso CP-02 es un hallazgo: un error real que el equipo debe corregir antes del despliegue. Probar con datos "malos" a propósito es justamente lo que diferencia a un buen tester.

La documentación técnica está dirigida a otros desarrolladores (incluido tu "yo" de dentro de seis meses). Su pieza central es el README: el archivo que cualquier persona lee primero al abrir tu repositorio. Un README completo para tu proyecto integrador debe responder cinco preguntas: qué es, qué necesita, cómo se instala, cómo se usa y cómo está organizado. 

# Sistema de Reservas "AgendaYa"

Aplicación web para gestionar reservas de canchas deportivas.
Proyecto integrador — Técnico Profesional en Programación Web.

## Requisitos
- Node.js 18 o superior
- MySQL 8

## Instalación
1. Clonar el repositorio: git clone https://github.com/equipo/agendaya.git
2. Instalar dependencias: npm install
3. Copiar .env.ejemplo como .env y completar las credenciales
4. Importar la base de datos: db/agendaya.sql

## Uso
- npm start inicia el servidor en http://localhost:3000
- Usuario de prueba: demo@correo.com / Demo1234

## Estructura del proyecto
- /public     → frontend (HTML, CSS, JS)
- /src/rutas  → endpoints del backend
- /db         → script SQL de la base de datos

La otra mitad de la documentación técnica son los comentarios en el código. Un buen comentario explica el porqué de una decisión, no repite lo obvio. Compara: // suma 1 a i no aporta nada, mientras que // Se valida aquí y no en el frontend porque el usuario puede desactivar JavaScript le ahorra horas a quien mantenga el código. Documenta especialmente las funciones públicas, las reglas de negocio y cualquier solución que no sea evidente.

El manual de usuario se escribe para la persona que va a usar la aplicación, no para quien la programó. Esa persona no sabe qué es un endpoint ni le interesa: quiere saber cómo registrarse, cómo hacer una reserva y qué hacer si olvidó su contraseña. Por eso el manual usa lenguaje cotidiano, va paso a paso y se apoya en capturas de pantalla.

3. Cómo hacer una reserva

  1. Ingresa a la aplicación con tu correo y contraseña.
  2. En el menú principal, haz clic en Nueva reserva.
  3. Elige la cancha, la fecha y la hora disponibles (las horas ocupadas aparecen en gris).
  4. Haz clic en el botón verde Confirmar reserva.
  5. Verás el mensaje "Reserva creada" y recibirás la confirmación en tu correo.

💡 ¿Problemas? Si la hora que quieres aparece en gris, ya fue reservada por otra persona: intenta con otro horario.

Un buen manual de usuario incluye: requisitos para usar la aplicación (navegador, conexión), cómo ingresar, una sección por cada función principal con pasos numerados y capturas, y una lista de preguntas frecuentes o problemas comunes con su solución.

Desplegar es publicar tu aplicación en un servidor de internet para que funcione sin depender de tu computador. Antes de publicar hay que preparar el entorno:

  • Variables de entorno: las contraseñas de la base de datos, llaves de API y URLs nunca van escritas en el código. Se guardan en un archivo .env (que se agrega a .gitignore para no subirlo al repositorio) y en producción se configuran en el panel del servicio de hosting.
  • Dependencias declaradas: el archivo package.json (Node.js) o composer.json (PHP) debe listar todo lo que el proyecto necesita, para que el servidor pueda instalarlo con un solo comando.
  • Configuración de producción: desactivar mensajes de depuración, usar la URL real del backend en el frontend y verificar que la base de datos de producción tenga las tablas creadas.

Opciones gratuitas para estudiantes:

🌐 GitHub Pages

Publica el frontend estático (HTML, CSS, JS) directamente desde tu repositorio. Ideal si tu frontend consume un backend alojado en otro servicio.

⚙️ Render / Railway

Alojan el backend (Node.js, Python, PHP…) conectado a tu repositorio: cada push puede volver a desplegar automáticamente la aplicación.

🗄️ Bases de datos gestionadas

Los mismos Render y Railway (y servicios como Aiven o Neon) ofrecen PostgreSQL o MySQL con planes gratuitos: te dan las credenciales que configuras como variables de entorno.

Lista de chequeo antes de decir "está publicado":

  • ☑️ El código está en el repositorio, sin archivos .env ni contraseñas subidas.
  • ☑️ Las variables de entorno están configuradas en el panel del hosting.
  • ☑️ La base de datos de producción existe y tiene sus tablas creadas.
  • ☑️ El frontend apunta a la URL real del backend (no a localhost).
  • ☑️ Los casos de prueba principales se repitieron sobre la URL pública y pasan.
  • ☑️ El README incluye el enlace de la aplicación desplegada.
