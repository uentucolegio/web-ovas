🚀 Autenticación, autorización y gestión de sesiones

La autenticación y la autorización constituyen el primer perímetro de defensa de cualquier aplicación web: antes de poder proteger los datos, es necesario establecer con certeza quién es el usuario que interactúa con el sistema y qué acciones tiene permitido realizar. Según informes recientes, una gran parte de las filtraciones de datos involucran credenciales comprometidas o mecanismos de autenticación débiles.

En esta OVA revisaremos las diferencias conceptuales entre autenticación y autorización, los flujos modernos de autenticación (incluyendo JWT), buenas prácticas de gestión de sesiones y mecanismos de autenticación multifactor. El objetivo es que puedas aplicar estas prácticas en proyectos reales y reducir la superficie de ataque relacionada con identidades y sesiones.

✨ Objetivo práctico: al finalizar, podrás diseñar e implementar un sistema de autenticación y gestión de sesiones con controles básicos de seguridad. 🔐

🎯 Objetivos de aprendizaje

  • 🔍 Diferenciar con precisión los conceptos de autenticación y autorización.
  • 🛡️ Comprender los principales mecanismos de autenticación modernos, incluyendo JWT y MFA.
  • 🔧 Aplicar buenas prácticas de gestión segura de sesiones en aplicaciones web.

Aunque frecuentemente se mencionan juntos, autenticación y autorización son procesos conceptualmente distintos que ocurren en momentos diferentes del flujo de una aplicación. Confundirlos es una fuente común de errores de diseño.

Figura 1. Diferencias conceptuales entre autenticación (verificar identidad) y autorización (verificar permisos). Fuente: elaboración propia mediante Python (Matplotlib).

🔑 La autenticación responde a la pregunta "¿quién eres?" y ocurre típicamente una sola vez, al inicio de la sesión del usuario, mediante la verificación de credenciales como usuario y contraseña, un token biométrico o un segundo factor de verificación.

🚦 La autorización, en cambio, responde a la pregunta "¿qué puedes hacer?" y se evalúa de forma constante durante toda la sesión, cada vez que el usuario intenta acceder a un recurso o ejecutar una acción específica dentro del sistema.

💡 Tip práctico: si tu API responde 401 es un problema de autenticación (no sabemos quién eres); si responde 403 es de autorización (sabemos quién eres, pero no tienes permiso). 🔐

JWT se ha convertido en el estándar predominante para la autenticación en arquitecturas API y SPAs. Recuerda que el payload no está cifrado, solo codificado en Base64, por lo que no debe contener información sensible.

Figura 2. Flujo completo de autenticación mediante JSON Web Token (JWT), desde el login hasta el acceso a recursos protegidos. Fuente: elaboración propia mediante Python (Matplotlib).

🧩 Un token JWT está compuesto por tres partes separadas por puntos: el encabezado (header), que especifica el algoritmo de firma; la carga útil (payload), que contiene los datos del usuario (claims) como su identificador y rol; y la firma (signature), que garantiza que el token no ha sido alterado desde su emisión.

⏳ Los tokens JWT deben tener un tiempo de expiración razonablemente corto. En aplicaciones que requieren mayor seguridad es recomendable implementar un mecanismo de refresh tokens que permita renovar el acceso sin que el usuario deba autenticarse nuevamente cada pocos minutos, equilibrando así la seguridad con una buena experiencia de usuario.

🧱 Concepto ❓ Pregunta que responde 📌 Ejemplo
Header (encabezado) ¿Qué algoritmo de firma se usó? HS256, RS256
Payload (carga útil) ¿Quién es el usuario y qué rol tiene? {"id": 123, "rol": "admin"}
Signature (firma) ¿El token fue alterado desde su emisión? Verificación con clave secreta/privada
Expiración (exp) ¿Cuándo deja de ser válido el token? exp: 900 (15 min)
Refresh token ¿Cómo renovar el acceso sin reautenticarse? Token de larga duración para solicitar un nuevo JWT

⚠️ Recuerda: el payload de un JWT no está cifrado, solo codificado en Base64, por lo que nunca debe incluirse información sensible (contraseñas, números de tarjeta, etc.) dentro de él. 🚫🔓

Código de ejemplo: fragmento ilustrativo (Node.js) incluido únicamente para mostrar cómo se genera y verifica un JWT en el servidor. No es código de producción; su objetivo es explicar los pasos básicos: crear el payload, firmarlo y verificar la firma.

// Ejemplo: generar/verificar JWT (Node.js, jsonwebtoken)
const jwt = require('jsonwebtoken');

const claveSecreta = process.env.JWT_SECRET;  // nunca hardcodear la clave

function generarToken(idUsuario, rol, clave) {
    const payload = { sub: idUsuario, rol: rol, iat: Math.floor(Date.now() / 1000) };
    return jwt.sign(payload, clave, { algorithm: 'HS256', expiresIn: '1h' });
}

function verificarToken(token, clave) {
    try { return jwt.verify(token, clave, { algorithms: ['HS256'] }); }
    catch (error) { return null; }
}

La gestión de sesión adecuada incluye identificadores no predecibles, expiración razonable, regeneración tras login y atributos de cookie como HttpOnly y Secure.

Figura 3. Comparativa entre prácticas inseguras y prácticas seguras en la gestión de sesiones web. Fuente: elaboración propia mediante Python (Matplotlib).

🎲 Un identificador de sesión predecible permite a un atacante adivinar o calcular sesiones de otros usuarios.

⏱️ La ausencia de tiempo de expiración mantiene sesiones activas indefinidamente, incrementando la ventana de oportunidad para un secuestro de sesión (session hijacking).

🍪 La falta de los atributos HttpOnly y Secure en las cookies de sesión expone el identificador a ataques de scripting entre sitios (XSS) y a interceptación en redes no cifradas, respectivamente.

✅ Buenas prácticas mínimas: generar IDs de sesión aleatorios y largos, expirar sesiones inactivas, regenerar el ID tras el login y marcar siempre las cookies como HttpOnly + Secure. 🛡️

La MFA combina factores independientes: algo que sabes, algo que tienes y algo que eres. Evita combinar dos factores de la misma categoría si buscas seguridad real.

Figura 4. Las tres categorías de factores de autenticación: algo que sabes, algo que tienes y algo que eres. Fuente: elaboración propia mediante Python (Matplotlib).

🚫 Es fundamental notar que combinar dos factores de la misma categoría —por ejemplo, una contraseña y una pregunta secreta, ambas pertenecientes a "algo que sabes"— no constituye verdadera autenticación multifactor, ya que un atacante que obtiene un factor de esa categoría probablemente puede obtener el otro mediante técnicas similares como phishing o ingeniería social.

📲 Ejemplo real: contraseña (algo que sabes) + código OTP enviado a tu celular o app autenticadora (algo que tienes) sí es MFA genuina, porque combina dos categorías independientes. ✅

Algoritmos como MD5/SHA-1 son inseguros para contraseñas; en su lugar usa bcrypt, Argon2 u otros diseñados para hashing de contraseñas con costo computacional ajustable.

Figura 5. Comparativa de algoritmos de hash para almacenamiento de contraseñas, de los obsoletos a los recomendados actualmente. Fuente: elaboración propia mediante Python (Matplotlib).

⚡ Algoritmos como MD5 y SHA-1 fueron diseñados originalmente para verificar la integridad de archivos a alta velocidad, característica que los hace inadecuados para contraseñas, ya que esa misma velocidad permite a un atacante probar miles de millones de combinaciones por segundo.

🐢 Algoritmos como bcrypt y Argon2, en cambio, fueron diseñados deliberadamente para ser computacionalmente costosos, dificultando los ataques de fuerza bruta incluso con hardware especializado.

🔒 Regla de oro: nunca almacenes contraseñas en texto plano ni con hashes "rápidos" (MD5/SHA-1/SHA-256 solo). Usa siempre bcrypt o Argon2 con un factor de costo adecuado. 🧂

Algoritmo Seguridad (comentario) Recomendación
Argon2 Diseñado para hashing de contraseñas, resistencia a GPU Recomendado (mejor opción 2025)
bcrypt Maduro, configurable con factor de coste Recomendado
SHA-256 (solo) Rápido, no apto solo para contraseñas No usar solo, combinar con KDF
SHA-1 / MD5 Obsoletos; vulnerables a colisiones NO usar
