🔐 Autorización y Control de Acceso en APIs

Las APIs REST se han convertido en el estándar arquitectónico dominante para la comunicación entre aplicaciones web modernas, ya sea entre el frontend y el backend de una misma aplicación, entre sistemas internos de una organización, o entre servicios de terceros. Esta omnipresencia convierte al control de acceso en APIs en una competencia crítica: según el OWASP API Security Top 10, las fallas de autorización a nivel de objeto (Broken Object Level Authorization) constituyen la vulnerabilidad más reportada específicamente en APIs.

En Colombia, el crecimiento del modelo de "banca abierta" (open banking) impulsado por el Ministerio TIC y la Superintendencia Financiera ha multiplicado la cantidad de APIs financieras expuestas que requieren mecanismos de autorización extremadamente rigurosos. Empresas como Bold, Addi y las fintechs emergentes de Bogotá y Medellín construyen su modelo de negocio completo alrededor de APIs seguras, estableciendo un estándar de calidad técnica que también influye en proyectos de menor escala desarrollados en la región Caribe colombiana.

Para el técnico en programación web de la Universidad de Córdoba, comprender cómo proteger correctamente una API REST es una habilidad que trasciende cualquier framework: ya sea construyendo APIs propias en Node.js o consumiendo APIs de terceros, entender los principios de autorización resulta indispensable para cualquier desarrollo web profesional contemporáneo.

✨ Al terminar este OVA sabrás implementar RBAC, usar correctamente los códigos 401 y 403, y comprenderás cómo OAuth 2.0 y el API Gateway protegen APIs reales. 🚀

Objetivos de aprendizaje

  • 🧠 Implementar mecanismos de control de acceso basado en roles (RBAC) en APIs REST, restringiendo el acceso a recursos según el perfil del usuario autenticado.
  • 💡 Aplicar correctamente los códigos de estado HTTP relacionados con autorización, comunicando con precisión la naturaleza de un fallo de acceso al cliente de la API.
  • 🔧 Explicar el flujo de autorización delegada mediante OAuth 2.0, distinguiendo el rol de cada actor involucrado en el protocolo.
  • 📦 Justificar el rol del API Gateway como punto centralizado de control de acceso en arquitecturas de microservicios, valorando su aporte al diseño de APIs seguras.

El modelo RBAC (Role-Based Access Control) es el enfoque de autorización más extendido en aplicaciones web y APIs REST, debido a su equilibrio entre simplicidad conceptual y flexibilidad práctica para gestionar permisos en sistemas con múltiples tipos de usuarios.

Figura 1. Modelo de Control de Acceso Basado en Roles (RBAC): usuarios asignados a roles, y roles asociados a permisos específicos. Fuente: elaboración propia mediante Python (Matplotlib).

🧩 En lugar de asignar permisos individualmente a cada usuario —lo cual se vuelve inmanejable a medida que el sistema crece— el modelo RBAC introduce una capa intermedia de "roles" (administrador, editor, lector, entre otros) que agrupan conjuntos coherentes de permisos.

🔗 Los usuarios se asignan a uno o varios roles, y los permisos efectivos de cada usuario se determinan por la unión de los permisos de todos sus roles asignados, simplificando enormemente la administración del sistema. ✅

El protocolo HTTP define códigos de estado específicos que una API REST debe utilizar correctamente para comunicar al cliente el resultado de una verificación de autenticación o autorización. El uso incorrecto de estos códigos es una fuente común de confusión y de posibles fugas de información.

Figura 2. Códigos de estado HTTP relevantes para el control de acceso en APIs REST y su significado correcto. Fuente: elaboración propia mediante Python (Matplotlib).

⚠️ Es importante distinguir con precisión entre el código 401 (Unauthorized), que en realidad indica un problema de autenticación —el cliente no ha probado quién es, o sus credenciales son inválidas o han expirado— y el código 403 (Forbidden), que indica un problema de autorización —el cliente ha sido autenticado correctamente, pero no tiene permiso para acceder al recurso solicitado.

El siguiente ejemplo implementa un middleware de autorización basado en roles para una API REST en Node.js/Express, que verifica tanto la validez del token como el permiso específico requerido:

// Middleware de autorización RBAC para endpoints protegidos
function requerirRol(rolesPermitidos) {
    return (req, res, next) => {
        const token = obtenerTokenDesdeHeader(req);
        const payload = verificarToken(token, process.env.JWT_SECRET);

        if (payload === null) {
            return res.status(401).json({ error: "Token inválido o ausente" });
        }
        if (!rolesPermitidos.includes(payload.rol)) {
            return res.status(403).json({ error: "No tiene permisos para este recurso" });
        }
        next();
    };
}

// Uso en un endpoint que solo el rol "administrador" puede ejecutar
app.get("/admin/reportes", requerirRol(["administrador"]), (req, res) => {
    // ... lógica del endpoint protegido
});
Código 1. Middleware de autorización RBAC que verifica autenticación (401) y permisos por rol (403) en una API REST con Node.js/Express.

OAuth 2.0 es el estándar de la industria para la autorización delegada, permitiendo que una aplicación obtenga acceso limitado a recursos de un usuario en otro sistema, sin que el usuario tenga que compartir sus credenciales directamente con la aplicación solicitante. Es el mecanismo detrás de "Iniciar sesión con Google" o la integración con APIs de redes sociales.

Figura 3. Flujo simplificado de autorización OAuth 2.0 (Authorization Code Flow) entre usuario, aplicación cliente, servidor de autorización y API protegida. Fuente: elaboración propia mediante Python (Matplotlib).

🛡️ El flujo de código de autorización (Authorization Code Flow), el más utilizado y seguro, garantiza que las credenciales del usuario nunca sean expuestas a la aplicación cliente: toda la verificación de identidad ocurre exclusivamente entre el usuario y el servidor de autorización de confianza, mientras que la aplicación cliente únicamente recibe un token de acceso limitado en alcance y duración. 🔒

En arquitecturas de microservicios, donde una aplicación se descompone en múltiples servicios independientes, el API Gateway emerge como un componente arquitectónico que centraliza las preocupaciones transversales de seguridad, evitando que cada microservicio individual deba reimplementar su propia lógica de autenticación y autorización.

Figura 4. El API Gateway actuando como punto único de entrada que centraliza autenticación, autorización, rate limiting y logging antes de distribuir las peticiones a los microservicios. Fuente: elaboración propia mediante Python (Matplotlib).

💡 Para proyectos de menor escala que no requieren microservicios, los principios del API Gateway pueden aplicarse igualmente mediante un middleware centralizado dentro de una única aplicación monolítica, validando autenticación y autorización en un punto único antes de delegar la petición a los controladores. 🧩

Una herramienta de diseño extremadamente útil antes de implementar el control de acceso en código es construir una matriz de permisos que cruce los roles del sistema con las operaciones CRUD permitidas, facilitando la detección temprana de inconsistencias.

Figura 5. Matriz de permisos CRUD que cruza los roles del sistema con las operaciones de creación, lectura, actualización y eliminación permitidas. Fuente: elaboración propia mediante Python (Matplotlib).

🎯 Diseñar esta matriz explícitamente antes de escribir código, en lugar de tomar decisiones de permisos de forma improvisada, reduce significativamente el riesgo de Broken Access Control (A01:2021), la categoría más crítica del OWASP Top 10 actual. 🛡️
