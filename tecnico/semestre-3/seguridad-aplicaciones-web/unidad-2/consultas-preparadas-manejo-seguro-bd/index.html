🗄️ Consultas Preparadas y Manejo Seguro de Bases de Datos

Mientras que el tema anterior de esta unidad introdujo el concepto y la lógica de las consultas preparadas como mecanismo de prevención de inyección SQL, este tema profundiza en su implementación práctica completa, abarcando las cuatro operaciones fundamentales de manipulación de datos (CRUD: Create, Read, Update, Delete) y extendiendo el análisis hacia otros aspectos críticos del manejo seguro de bases de datos: la gestión de credenciales y el cifrado de datos sensibles.

La gestión inadecuada de credenciales de bases de datos, incluyendo contraseñas codificadas directamente en el código fuente (hardcoded) y posteriormente subidas a repositorios públicos de GitHub, ha sido la causa de numerosos incidentes de seguridad documentados públicamente a nivel global. Este riesgo no es exclusivo de grandes corporaciones: pequeñas y medianas empresas que suben accidentalmente las credenciales completas de sus bases de datos de producción a repositorios públicos exponen directamente la información de sus clientes, un escenario particularmente relevante para el tejido empresarial de ciudades intermedias como Montería, donde muchos sistemas se desarrollan sin la supervisión de especialistas en seguridad.

Para el técnico en programación web de la Universidad de Córdoba, dominar el manejo seguro de bases de datos en su totalidad —desde la consulta individual hasta la gestión de credenciales y el cifrado de información sensible— constituye el cierre natural de las competencias técnicas centrales del curso.

✨ Al terminar este OVA sabrás implementar CRUD completo con consultas preparadas, gestionar credenciales mediante variables de entorno, y comprenderás cuándo y cómo cifrar datos sensibles. 🔐

Objetivos de aprendizaje

  • 🧠 Aplicar consultas preparadas mediante Node.js (pg/mysql2) en operaciones CRUD completas, integrándolas de forma consistente en la interacción con la base de datos.
  • 💡 Gestionar de forma segura las credenciales de conexión a bases de datos mediante variables de entorno, evitando su exposición en el código fuente.
  • 🔧 Diseñar esquemas de acceso a datos robustos aplicando los principios de cifrado de datos tanto en tránsito como en reposo.
  • 📦 Justificar por qué cifrar la totalidad de los campos de una base de datos no constituye necesariamente una práctica recomendada, a pesar del beneficio aparente en seguridad.

Comprender el ciclo completo de ejecución interno de una consulta preparada permite entender con mayor profundidad por qué este mecanismo previene estructuralmente la inyección SQL, más allá de la simple recomendación de "usar consultas parametrizadas en lugar de concatenar strings".

Figura 1. Las cuatro fases del ciclo de ejecución de una consulta preparada: preparar, vincular, ejecutar y recuperar resultados. Fuente: elaboración propia mediante Python (Matplotlib).

🧩 La separación temporal entre la fase de preparación (donde el motor analiza y compila la estructura de la consulta) y la fase de vinculación de valores (donde los datos del usuario se incorporan exclusivamente como parámetros literales) es la razón estructural por la cual ningún valor proporcionado por el usuario puede alterar la lógica SQL, sin importar qué caracteres especiales contenga. 🔒

Las credenciales de acceso a la base de datos —usuario, contraseña, host y nombre de la base de datos— representan información extremadamente sensible que, de ser expuesta, otorga a un atacante acceso directo y completo a todos los datos de la aplicación, haciendo irrelevantes todas las demás medidas de seguridad implementadas en el código.

Figura 2. Comparación entre la práctica insegura de codificar credenciales directamente en el código fuente y la práctica segura de utilizar variables de entorno externas al repositorio. Fuente: elaboración propia mediante Python (Matplotlib).

📁 La práctica recomendada consiste en almacenar las credenciales en un archivo de variables de entorno (típicamente .env) que se excluye explícitamente del control de versiones mediante el archivo .gitignore, de modo que estas nunca lleguen a un repositorio compartido.

🏦 En entornos de producción profesionales, estas credenciales se gestionan idealmente mediante servicios especializados de gestión de secretos (vaults) que añaden capas adicionales de control de acceso y auditoría. 🔐

Las cuatro operaciones fundamentales de manipulación de datos en una aplicación web —crear, leer, actualizar y eliminar registros— deben implementarse de forma consistente utilizando consultas preparadas en todos los casos, sin excepción, independientemente de si el dato de entrada proviene directamente de un formulario o de un cálculo interno de la aplicación.

Figura 3. Las cuatro operaciones CRUD (Create, Read, Update, Delete) implementadas mediante consultas preparadas con parámetros vinculados. Fuente: elaboración propia mediante Python (Matplotlib).

📏 Es una práctica recomendable establecer como estándar de equipo que ninguna consulta SQL se escriba jamás mediante concatenación directa de variables, sin importar cuán "seguro" parezca el origen del dato, ya que la disciplina consistente reduce significativamente el riesgo de errores humanos.

El siguiente ejemplo integra todo lo desarrollado en esta guía en una clase de acceso a datos (Data Access Object) completa, que centraliza las cuatro operaciones CRUD para una entidad, gestionando la conexión mediante variables de entorno y utilizando exclusivamente consultas parametrizadas:

const { Pool } = require("pg");

class UsuarioDAO {
    constructor() {
        this.pool = new Pool({
            host: process.env.DB_HOST,
            database: process.env.DB_NAME,
            user: process.env.DB_USER,
            password: process.env.DB_PASS,
        });
    }

    async crear(nombre, email) {
        const resultado = await this.pool.query(
            "INSERT INTO usuarios (nombre, email) VALUES ($1, $2) RETURNING id",
            [nombre, email]
        );
        return resultado.rows[0].id;
    }

    async obtenerPorId(id) {
        const resultado = await this.pool.query(
            "SELECT * FROM usuarios WHERE id = $1",
            [id]
        );
        return resultado.rows[0] || null;
    }

    async actualizar(id, nombre) {
        const resultado = await this.pool.query(
            "UPDATE usuarios SET nombre = $1 WHERE id = $2",
            [nombre, id]
        );
        return resultado.rowCount > 0;
    }

    async eliminar(id) {
        const resultado = await this.pool.query(
            "DELETE FROM usuarios WHERE id = $1",
            [id]
        );
        return resultado.rowCount > 0;
    }
}

module.exports = UsuarioDAO;
Código 1. Clase de acceso a datos (DAO) con las cuatro operaciones CRUD implementadas mediante consultas parametrizadas en Node.js (pg).

La protección integral de los datos de una aplicación requiere considerar dos estados distintos en los que la información puede encontrarse vulnerable: mientras viaja por la red (en tránsito) y mientras permanece almacenada en el servidor (en reposo), cada uno requiriendo mecanismos de cifrado específicos.

Figura 4. Comparación entre el cifrado de datos en tránsito (protocolo TLS/HTTPS) y el cifrado de datos en reposo (almacenamiento cifrado en base de datos). Fuente: elaboración propia mediante Python (Matplotlib).

🌐 El cifrado en tránsito se implementa principalmente mediante el protocolo TLS, que protege HTTPS y también puede configurarse para cifrar la conexión específica entre la aplicación y el servidor de base de datos.

💾 El cifrado en reposo protege los datos almacenados físicamente en disco, e incluye desde el hash irreversible de contraseñas (que técnicamente no es cifrado sino una transformación unidireccional) hasta el cifrado simétrico de campos específicamente sensibles como números de documento de identidad o información médica. 🧬

Más allá de usar consultas preparadas, la seguridad del acceso a la base de datos depende también de cómo se configura la conexión misma, siendo importante comprender el propósito específico de cada componente de las credenciales de conexión.

Figura 5. Componentes de una cadena de conexión segura a base de datos: host, nombre de base de datos, usuario y contraseña. Fuente: elaboración propia mediante Python (Matplotlib).

⚠️ Cada uno de estos cuatro componentes representa una superficie de ataque potencial si se gestiona incorrectamente: un host expuesto directamente a internet sin restricciones de firewall, un usuario con privilegios excesivos, o una contraseña débil o filtrada en un repositorio público, pueden anular por completo todas las demás medidas de seguridad implementadas en el código. 🛡️
