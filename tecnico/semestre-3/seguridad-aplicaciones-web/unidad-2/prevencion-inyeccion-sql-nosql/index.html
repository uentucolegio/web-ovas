💉 Prevención de Inyección SQL y NoSQL

La inyección de código ha ocupado consistentemente un lugar entre las vulnerabilidades más críticas en cada edición del OWASP Top 10 desde su primera publicación en 2003, y continúa siendo, más de dos décadas después, una de las causas más frecuentes de filtraciones masivas de datos a nivel mundial. La razón de su persistencia no es la falta de soluciones técnicas conocidas —la prevención mediante consultas preparadas es una técnica bien establecida y documentada desde hace años—, sino la falta de aplicación consistente de estas técnicas por parte de los desarrolladores.

En el contexto colombiano, incidentes de inyección SQL han afectado a entidades de diversos sectores, desde pequeños comercios electrónicos hasta, en casos documentados por el CCP (Centro Cibernético Policial), portales gubernamentales municipales con infraestructura de desarrollo limitada. La proliferación de sistemas de gestión desarrollados internamente por pequeñas y medianas empresas de ciudades intermedias como Montería, sin la supervisión de especialistas en seguridad, incrementa significativamente la exposición a este tipo de vulnerabilidad en el tejido empresarial regional.

Para el estudiante del Técnico Profesional en Programación Web, este tema representa una de las competencias técnicas más críticas de toda su formación: prácticamente cualquier aplicación que interactúe con una base de datos —que es la inmensa mayoría de las aplicaciones web profesionales— requiere la implementación correcta de mecanismos de prevención de inyección.

✨ Al terminar este OVA sabrás identificar los distintos tipos de inyección y aplicarás consultas preparadas como tu defensa principal en cada consulta a base de datos. 🛡️

Objetivos de aprendizaje

  • 🧠 Explicar el funcionamiento técnico de los ataques de inyección SQL y NoSQL, reconociendo los puntos de la aplicación donde estos ataques suelen originarse.
  • 💡 Aplicar consultas preparadas como mecanismo principal de prevención de inyección, implementándolas de forma consistente en las operaciones con bases de datos.
  • 🔧 Identificar estrategias complementarias de defensa en profundidad contra inyección, fortaleciendo la resistencia de las aplicaciones backend ante una de las vulnerabilidades más críticas y persistentes en la historia de la seguridad web.
  • 📦 Justificar por qué la inyección SQL continúa siendo una de las vulnerabilidades más persistentes en el desarrollo web actual, a pesar de existir soluciones técnicas ampliamente documentadas.

Si bien la inyección SQL es la variante más conocida y documentada, el principio de inyección de código se manifiesta en múltiples contextos tecnológicos, todos compartiendo la misma causa raíz conceptual.

Figura 1. Tipos de ataques de inyección según el lenguaje o sistema objetivo: SQL, NoSQL, comandos del sistema operativo y LDAP. Fuente: elaboración propia mediante Python (Matplotlib).
Tipo Dónde ocurre Ejemplo de riesgo
SQL Injection Consultas a bases relacionales (MySQL, PostgreSQL, SQL Server) por concatenación Insertar ' OR '1'='1 evita la autenticación
NoSQL Injection Consultas documentales (MongoDB) con JSON del usuario sin validar Enviar {"$gt": ""} salta la validación de credenciales
Command Injection Llamadas del backend a comandos del SO (exec, system) sin sanitizar Agregar ; rm -rf / ejecuta comandos destructivos
LDAP Injection Consultas a directorios LDAP (Active Directory) sin escape Insertar *)(uid=*) devuelve todo el directorio

🧩 En todos los casos, la causa raíz es idéntica: el sistema mezcla código ejecutable (la consulta SQL, el comando del sistema, el filtro LDAP) con datos proporcionados por el usuario sin establecer una separación clara entre ambos. ⚠️

Las consultas preparadas (prepared statements) constituyen la técnica de prevención más efectiva y ampliamente recomendada contra la inyección SQL, ya que abordan el problema desde su causa estructural en lugar de intentar filtrar o escapar caracteres peligrosos después de que el daño potencial ya está presente en la cadena de texto.

Figura 2. Comparación entre una consulta SQL vulnerable construida por concatenación y una consulta preparada segura mediante parámetros vinculados. Fuente: elaboración propia mediante Python (Matplotlib).

⚙️ El principio fundamental es que el motor de base de datos primero recibe y compila la estructura de la consulta SQL (con marcadores de posición en lugar de valores reales), y solo después recibe los valores de los parámetros, los cuales se tratan exclusivamente como datos literales sin posibilidad de ser interpretados como código SQL ejecutable, sin importar qué caracteres especiales contengan.

El siguiente ejemplo amplía el concepto a un caso de uso completo: una función de búsqueda de usuarios por múltiples criterios opcionales, escenario común donde los desarrolladores principiantes suelen recurrir incorrectamente a la concatenación de cadenas:

// Búsqueda dinámica con múltiples filtros opcionales, 100% segura
async function buscarUsuarios(pool, filtros) {
    let sql = "SELECT id, nombre, email FROM usuarios WHERE 1=1";
    const params = [];

    if (filtros.nombre) {
        params.push(`%${filtros.nombre}%`);
        sql += ` AND nombre LIKE $${params.length}`;
    }
    if (filtros.rol) {
        params.push(filtros.rol);
        sql += ` AND rol = $${params.length}`;
    }

    const resultado = await pool.query(sql, params);
    return resultado.rows;
}
Código 1. Búsqueda dinámica con filtros opcionales construida de forma segura mediante consultas preparadas.

Con la creciente adopción de bases de datos NoSQL como MongoDB en aplicaciones web modernas, ha surgido una variante de inyección específica para estos sistemas, que explota la capacidad de los formatos de consulta basados en JSON para aceptar operadores especiales en lugar de valores literales esperados.

Figura 3. Ejemplo de inyección NoSQL en MongoDB mediante el operador $ne, y su mitigación mediante validación de tipos. Fuente: elaboración propia mediante Python (Matplotlib).

🚫 A diferencia de la inyección SQL tradicional, la inyección NoSQL no requiere caracteres especiales de escape sino el envío de objetos JSON con operadores del motor de base de datos (como $ne, $gt o $where) en lugar de los valores de texto plano que la aplicación espera recibir.

🔍 Esto subraya la importancia de validar estrictamente el tipo de dato de cada campo recibido, no únicamente su contenido. ✅

Si bien las consultas preparadas constituyen la defensa principal y obligatoria, una estrategia de seguridad robusta incorpora capas adicionales de protección que actúan como respaldo ante posibles errores humanos o escenarios no contemplados.

Figura 4. Cinco estrategias complementarias de defensa en profundidad contra ataques de inyección. Fuente: elaboración propia mediante Python (Matplotlib).

⚖️ Ninguna de estas estrategias sustituye a las consultas preparadas, sino que las complementan: incluso con consultas preparadas correctamente implementadas, otorgar al usuario de base de datos de la aplicación permisos administrativos completos sigue representando un riesgo innecesario. 🔑

Los ataques de inyección no se limitan a la interacción directa con la base de datos: pueden originarse en cualquier punto de la aplicación donde se reciba input externo, por lo que resulta útil mapear las distintas capas y puntos de entrada donde estos vectores de ataque pueden manifestarse.

Figura 5. Vectores de inyección según la capa de la aplicación donde se origina el dato: formularios, APIs, archivos subidos, base de datos y sistema operativo. Fuente: elaboración propia mediante Python (Matplotlib).

🎯 Cada punto de entrada requiere las mismas técnicas fundamentales de defensa: consultas preparadas para la base de datos, validación estricta de tipos y formatos, y sanitización de nombres de archivo, adaptadas al contexto específico de cada capa. Un atacante solo necesita encontrar un único punto de entrada desprotegido para comprometer la aplicación completa. 🕵️

const express = require("express");
const { Pool } = require("pg");
const app = express();
const pool = new Pool({ host: "localhost", user: "postgres", password: "", database: "tienda" });

app.get("/productos", async (req, res) => {
    const nombre = req.query.nombre;
    const categoria = req.query.categoria;
    const sql = "SELECT * FROM productos WHERE nombre LIKE '%" + nombre
        + "%' AND categoria = '" + categoria + "'";
    const resultado = await pool.query(sql);
    res.json(resultado.rows);
});
