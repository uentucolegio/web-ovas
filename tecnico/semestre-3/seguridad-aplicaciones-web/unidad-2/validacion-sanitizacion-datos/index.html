🛡️ Validación y Sanitización de Datos

Toda entrada de datos proveniente de un usuario o sistema externo debe considerarse, por principio, no confiable hasta que se demuestre lo contrario. Esta máxima, conocida en la industria como "never trust user input", constituye el fundamento conceptual de la validación y sanitización de datos, y es la primera línea de defensa contra la inmensa mayoría de las vulnerabilidades incluidas en el OWASP Top 10, incluyendo inyección SQL, Cross-Site Scripting (XSS) y diversas formas de manipulación de datos.

En el desarrollo backend con Node.js (Express) y bases de datos relacionales —stack tecnológico ampliamente utilizado en el ecosistema empresarial actual por su rendimiento en operaciones de E/S y la disponibilidad de talento capacitado— la validación y sanitización correcta de datos es particularmente crítica, dado que JavaScript, por su naturaleza de tipado dinámico, facilita errores sutiles si el desarrollador no es riguroso en la verificación explícita de los datos recibidos a través de formularios, parámetros de URL o cuerpos de petición JSON.

Para el técnico en programación web de la Universidad de Córdoba, dominar estas técnicas es una competencia de aplicación inmediata: prácticamente todo formulario web, desde un simple registro de usuario hasta un sistema complejo de gestión empresarial, requiere validar y sanitizar los datos antes de procesarlos o almacenarlos.

✨ Al terminar este OVA sabrás distinguir cuándo validar y cuándo sanitizar, y aplicarás ambos procesos con herramientas reales de Node.js en cada capa de tu aplicación. 🚀

Objetivos de aprendizaje

  • 🧠 Comparar los conceptos de validación y sanitización de datos de entrada, reconociendo el propósito y alcance de cada uno dentro del ciclo de vida de una petición web.
  • 💡 Implementar validaciones efectivas en las distintas capas de una aplicación web (cliente, servidor y base de datos), evitando depender de una sola línea de defensa.
  • 🔧 Aplicar funciones de validación, sanitización y escape de salida, protegiendo las aplicaciones contra datos maliciosos o malformados provenientes de fuentes no confiables.
  • 📦 Justificar la necesidad de aplicar validaciones también a nivel de base de datos (constraints), aun cuando ya exista una validación rigurosa del lado del servidor.

Aunque frecuentemente se mencionan en conjunto, validación y sanitización son procesos complementarios pero distintos que cumplen funciones diferentes dentro del flujo de procesamiento de datos de una aplicación.

Figura 1. Diferencias conceptuales entre validación (verificar corrección) y sanitización (limpiar el dato) de entradas de usuario. Fuente: elaboración propia mediante Python (Matplotlib).

✅ La validación responde a la pregunta "¿es correcto este dato?" y su resultado es binario: el dato se acepta o se rechaza según cumpla o no con las reglas establecidas (formato, tipo, rango, longitud).

🧹 La sanitización, en cambio, responde a la pregunta "¿cómo hago seguro este dato?" y su resultado es una transformación del dato original, eliminando o neutralizando los elementos potencialmente peligrosos sin necesariamente rechazar la entrada completa.

💡 Ejemplo rápido: un nombre de usuario con espacios de más se sanitiza (se recorta); un correo sin arroba se rechaza por validación. 🔀

Una estrategia de validación robusta no se limita a una única capa de la aplicación, sino que distribuye responsabilidades específicas entre el cliente, el servidor y la base de datos, reconociendo que cada capa cumple un propósito distinto y que únicamente la validación del lado del servidor puede considerarse una medida de seguridad real.

Figura 2. Validación distribuida en las tres capas de una aplicación web: cliente, servidor y base de datos. Fuente: elaboración propia mediante Python (Matplotlib).

💻 La validación en el cliente (JavaScript) mejora la experiencia de usuario al proporcionar retroalimentación inmediata, pero puede ser fácilmente eludida por un atacante que envíe peticiones directamente al servidor sin pasar por la interfaz web.

🖥️ La validación en el servidor es, por tanto, obligatoria y constituye la verdadera fuente de verdad de seguridad.

🗄️ Finalmente, las restricciones (constraints) a nivel de base de datos, como NOT NULL, CHECK o claves foráneas, actúan como la última barrera de protección ante cualquier dato que, por error de programación, haya logrado eludir las capas anteriores.

⚠️ Comprender esta arquitectura de defensa en capas evita el error común de desarrolladores principiantes que, al confiar exclusivamente en la validación del lado del cliente, exponen su aplicación a manipulaciones triviales mediante herramientas como las consolas de desarrollador del navegador o clientes HTTP como Postman. 🛑

Existen patrones de validación recurrentes que se aplican según la naturaleza del dato que se está procesando, cada uno con su propia técnica de implementación en JavaScript/Node.js.

Figura 3. Seis tipos comunes de validación de datos de entrada con ejemplos de implementación en JavaScript/Node.js. Fuente: elaboración propia mediante Python (Matplotlib).

🏳️ Entre estos tipos, la validación por lista blanca (whitelist) es considerada la práctica más segura cuando es aplicable, ya que en lugar de intentar anticipar y bloquear todos los valores posibles maliciosos (lista negra), únicamente permite explícitamente los valores que se sabe que son legítimos, reduciendo significativamente el riesgo de que un valor inesperado o malicioso pase desapercibido.

El siguiente fragmento integra varias funciones de validación y sanitización vistas en esta sección, aplicadas en conjunto al procesamiento de un formulario de registro de usuario, mostrando el flujo completo desde la recepción del dato hasta su almacenamiento seguro:

// Validación y sanitización combinadas de un formulario de registro
const errores = [];

// 1. Sanitizar y validar el nombre
const nombre = (req.body.nombre || "").trim();
if (nombre.length < 2 || nombre.length > 80) {
    errores.push("El nombre debe tener entre 2 y 80 caracteres");
}

// 2. Validar formato de email
const email = validator.normalizeEmail(req.body.email || "");
if (!validator.isEmail(email)) {
    errores.push("El correo electrónico no es válido");
}

// 3. Validar edad dentro de un rango lógico
const edad = Number(req.body.edad);
if (!Number.isInteger(edad) || edad < 0 || edad > 120) {
    errores.push("La edad debe ser un número entre 0 y 120");
}

if (errores.length === 0) {
    // proceder a almacenar los datos validados y sanitizados
}
Código 1. Validación y sanitización combinadas de los campos de un formulario de registro en Node.js.

El ecosistema de Node.js ofrece bibliotecas ampliamente utilizadas para sanitizar y validar diferentes tipos de datos de entrada, las cuales todo desarrollador backend debe conocer y utilizar de forma sistemática.

Figura 4. Funciones de sanitización y validación más utilizadas en el desarrollo backend con Node.js. Fuente: elaboración propia mediante Python (Matplotlib).

🚫 Es importante destacar que la función validator.escape() es esencial para prevenir ataques de Cross-Site Scripting (XSS) al momento de mostrar datos proporcionados por el usuario en una página HTML.

🔗 Las consultas parametrizadas mediante bibliotecas como pg o mysql2 no son técnicamente una función de "sanitización", sino un mecanismo de separación entre código y datos que previene la inyección SQL de forma estructural.

🧠 Regla práctica: sanitiza lo que vas a mostrar (escape), valida lo que vas a guardar (isEmail, isInt...), y parametriza lo que vas a consultar en la base de datos. ✅

Habiendo estudiado por separado los conceptos de validación, sanitización y las capas donde estas se aplican, resulta útil consolidar todo el proceso en un único flujo visual que muestre la secuencia completa que sigue un dato desde que ingresa a la aplicación hasta que se almacena de forma segura.

Figura 5. Flujo completo de procesamiento seguro de un dato de entrada, desde su ingreso hasta su almacenamiento en base de datos. Fuente: elaboración propia mediante Python (Matplotlib).

🎯 Este flujo debe aplicarse de forma consistente a cada dato proporcionado por el usuario, sin excepciones, incluso en aquellos campos que parezcan de bajo riesgo a primera vista: la experiencia de la industria demuestra que los atacantes frecuentemente explotan precisamente los campos que los desarrolladores consideraron menos críticos y por tanto validaron con menor rigor. 🕵️
