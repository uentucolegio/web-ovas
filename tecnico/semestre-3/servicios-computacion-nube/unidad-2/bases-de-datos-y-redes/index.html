🗄️ Bases de datos y redes en la nube

Imagina que terminas de desplegar tu aplicación: el frontend está en S3, el backend corre en un servidor. Todo parece listo, pero cuando el usuario intenta registrarse, la aplicación no guarda nada. 😳 El problema no está en el código: no hay ninguna base de datos conectada. El backend tiene que guardar esa información en algún lugar, y ese lugar también tiene que estar en la nube.

Y hay un segundo problema justo después: si esa base de datos es accesible desde cualquier parte de internet, cualquiera podría intentar conectarse a ella. No solo tus usuarios; también atacantes. 🛡️ Ahí entra la red virtual privada que rodea tu aplicación: define quién puede hablar con quién, qué puertos están abiertos y qué recursos son públicos o privados.

Aquí vas a entender cómo funcionan las bases de datos gestionadas y los conceptos de red que conectan de forma segura los componentes de tu aplicación, y vas a practicar creando una base de datos real. 🚀

✨ Al terminar sabrás elegir la base de datos correcta y proteger su acceso con criterio de red. 🚀

Objetivos de aprendizaje

  • ⚖️Comparar las bases de datos gestionadas relacionales y NoSQL según el tipo de datos y el caso de uso.
  • 🌐Explicar la función de los componentes de red de la nube (VPC, subredes, grupos de seguridad y balanceadores de carga) en la conectividad segura de una aplicación web.
  • 🛠️Configurar una base de datos gestionada en la nube y consultar sus datos, aplicando criterios básicos de seguridad.

No hay una "mejor" base de datos: hay la adecuada para cada caso. Esta tabla resume cuándo brilla cada una 👇

🧮 Relacional (SQL)

Datos con relaciones claras (usuarios-pedidos-productos), consultas con JOINs, integridad y transacciones críticas. Ej.: PostgreSQL, MySQL.

📂 NoSQL

Datos muy variables en estructura, o escala masiva con lecturas simples clave-valor/documentos. Ej.: DynamoDB, Firestore.

La diferencia de fondo está en cómo tratan los datos. Las bases relacionales exigen definir por adelantado un esquema (qué tablas existen y qué columnas tiene cada una) y garantizan que cada operación se complete de forma íntegra: o se guarda todo, o no se guarda nada. Eso es vital, por ejemplo, en un banco, donde no puede "perderse" una transferencia a medias ni cobrarse dos veces.

Las bases NoSQL relajan esas reglas a cambio de flexibilidad y escala: cada registro puede tener campos distintos (útil cuando los datos cambian seguido) y la información se reparte con facilidad entre muchos servidores para atender a millones de usuarios. El precio es que, a veces, un dato recién escrito tarda un instante en verse igual en todas las copias. No es que una sea mejor que la otra: responden a prioridades distintas —integridad estricta frente a flexibilidad y escala—, y elegir bien es parte del diseño de la aplicación.

Un grupo de seguridad es un firewall que decide qué tráfico entra a cada recurso, por puerto y origen. Funciona con una lógica de "denegar por defecto": si no creas una regla que permita explícitamente un tipo de tráfico, ese tráfico queda bloqueado. Por eso la seguridad no consiste en "bloquear lo malo" (imposible de enumerar), sino en permitir solo lo estrictamente necesario y dejar cerrado todo lo demás.

Cada regla es específica por puerto y por origen. Un puerto es como una "puerta numerada" del servidor: el 443 es HTTPS (web segura), el 22 es SSH (administración remota) y el 5432 es PostgreSQL. No es lo mismo abrir el 443 a todo el mundo (normal en un sitio web) que abrir el 5432 a todo internet (un error grave). Y el origen importa: puedes permitir un puerto solo desde una IP concreta —por ejemplo, que a la base de datos solo llegue el backend—. Combinar varias capas (red privada + grupos de seguridad + contraseñas fuertes) es lo que se llama defensa en profundidad: si una capa falla, las otras siguen protegiendo.

Ponte en el rol de administrador: decide si cada regla se debe permitir o bloquear. Cada acierto suma 25 puntos. 👇

Cada año se filtran millones de registros personales por un error tan simple como dejar una base de datos accesible en internet sin contraseña. Bots automáticos escanean la red buscando justamente eso. Por eso las decisiones de red (subred privada, grupos de seguridad) no son "opcionales".

¿Y cómo ocurren estas filtraciones? No hace falta un hacker sofisticado. Existen buscadores especializados y programas automáticos que recorren internet las 24 horas catalogando servidores con puertos abiertos. Si una base de datos quedó accesible sin contraseña —a veces por dejar una configuración de prueba en producción—, esos bots la encuentran en minutos, copian su contenido y en ocasiones lo borran pidiendo un rescate. La lección para un desarrollador es clara: la seguridad de los datos no es una tarea para "el final" del proyecto, sino una decisión de arquitectura desde el inicio.

🐘 Actividad 1: Laboratorio — Crea y consulta una base de datos PostgreSQL gratuita

Crea una cuenta en Neon (neon.tech, PostgreSQL gestionado gratis sin tarjeta) y un proyecto. En el SQL Editor crea una tabla usuarios (id, nombre, email, fecha_registro), inserta 3 registros de prueba, y ejecuta consultas SELECT (todas y con filtro LIKE). Copia la cadena de conexión. Responde: ¿instalaste PostgreSQL en tu equipo? ¿Qué necesitarías para conectarla a un backend Node.js y dónde guardarías la cadena de conexión? ¿Qué pasaría con tus datos si Neon tuviera un fallo de hardware?

📝 Producto esperado: captura del SQL Editor con el resultado del SELECT + respuestas a las tres preguntas.

🔎 Actividad 2: Comparación de bases de datos gestionadas

Compara cuatro opciones de PostgreSQL gestionado para el proyecto integrador: AWS RDS, Google Cloud SQL, Neon y Supabase. Para cada una: ¿tiene capa gratuita y con qué límites? ¿requiere tarjeta de crédito? ¿qué región más cercana a Colombia ofrece?

📝 Producto esperado: tabla comparativa de las cuatro opciones + recomendación fundamentada para el proyecto integrador.

📐 Actividad 3: Diagrama de arquitectura de red

Diseña el diagrama de red del proyecto integrador (frontend + backend API + base de datos) mostrando: una VPC con subredes pública y privada, en qué subred va cada componente (frontend fuera de la VPC; backend en pública; base de datos en privada), los grupos de seguridad de cada componente y qué tráfico permiten, y el flujo de una petición del navegador hasta la base de datos.

📝 Producto esperado: diagrama exportado como imagen con anotaciones que explican las decisiones de seguridad.

🧠 Actividad 4: Investigación — ¿Cuándo usar NoSQL?

Investiga un caso real de una empresa que migró de relacional a NoSQL (o viceversa) y por qué. Luego decide para el proyecto integrador: ¿sus datos (usuarios, contenido, historial) se representan mejor como tablas relacionales o documentos NoSQL? ¿Qué pasaría si necesitaras guardar datos muy variables por usuario (configuraciones personalizadas)?

📝 Producto esperado: resumen de media página del caso real + decisión justificada del tipo de base de datos para el proyecto.

🧩 Actividad 5: Cuestionario de comprensión

Responde individualmente: ¿qué diferencia hay entre instalar PostgreSQL en una VM propia y usar Amazon RDS? ¿Cuándo tiene sentido NoSQL en vez de relacional (con un ejemplo de cada)? ¿Qué es una VPC y por qué importa para la seguridad? Explica la diferencia entre subred pública y privada y en cuál pondrías la base de datos. ¿Qué reglas tendría el grupo de seguridad de un PostgreSQL en producción? ¿Para qué sirve un balanceador de carga?
