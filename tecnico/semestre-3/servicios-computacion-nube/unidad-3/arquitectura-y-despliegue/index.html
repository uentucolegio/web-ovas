🚀 Arquitectura y despliegue en la nube

Durante las guías anteriores aprendiste a reconocer los servicios de cómputo, almacenamiento, bases de datos y redes que ofrece la nube. Llegó el momento de unir todas esas piezas y hacer algo que quizás solo habías hecho en tu propio computador: poner una aplicación en funcionamiento para que cualquier persona del mundo pueda usarla. 🌍

Piénsalo así: mientras tu proyecto corre en localhost, es como una obra de teatro ensayada en tu sala, con público de una sola persona: tú. 🎭 Desplegar en la nube es abrir el telón en un teatro real, con las puertas abiertas al público. Y para que la función salga bien, cada parte de la aplicación —la que se ve, la que piensa y la que recuerda— tiene que estar montada en el lugar adecuado.

Aquí vas a repasar cómo se organiza una aplicación web en capas, entender qué significa realmente "desplegar" (en inglés, deploy) y llevar a la práctica el despliegue del frontend y del backend en servicios gratuitos. Es el primer gran paso del proyecto integrador: pasar de "funciona en mi máquina" a "funciona en internet". 💻➡️🌐

✨ Al terminar tendrás tu aplicación viva en internet, con una URL que podrás compartir. 🚀

Objetivos de aprendizaje

  • 🧠Analizar la arquitectura de una aplicación web (frontend, backend y base de datos) para planificar su despliegue en la nube.
  • 🚀Desplegar el frontend y el backend de una aplicación web en servicios de la nube, dejándolos accesibles desde internet.
  • 🎯Justificar la elección del servicio de despliegue para cada componente según sus características y su costo.

Cuando ejecutas tu proyecto en localhost, solo existe mientras tu computador está encendido y solo tú puedes verlo. Desplegar (deploy) es poner ese código a correr en un servidor accesible desde internet, de forma permanente y con una URL pública. No es "subir archivos": implica que un servicio mantenga tu aplicación encendida, la reinicie si se cae y la entregue a los usuarios.

Aquí aparece un concepto que usarás toda tu carrera: los entornos. El de desarrollo es tu localhost, donde experimentas sin miedo a romper nada. El de producción (production) es el que usan las personas reales, donde un error sí tiene consecuencias. Muchos equipos añaden un entorno intermedio de pruebas llamado staging. Mantenerlos separados evita que un experimento a medio terminar afecte a tus usuarios.

💡 Idea clave: "funciona en mi máquina" no es lo mismo que "funciona en producción". El objetivo del despliegue es cerrar esa brecha: que funcione para cualquiera, en cualquier lugar, siempre.

El despliegue moderno además suele ser continuo (continuous deployment): conectas tu repositorio de GitHub a la plataforma y, cada vez que subes un cambio con git push, la aplicación se actualiza sola. Recorre el flujo completo 👇

La clave del despliegue en la nube es que cada capa va al servicio que mejor le conviene, no todas al mismo sitio. El motivo es su naturaleza distinta:

🖼️ Frontend

Son archivos (HTML/CSS/JS) que se ejecutan en el navegador. Se despliegan en un hosting estático (Vercel, Netlify, S3): barato y rapidísimo.

🧠 Backend

Es un programa que corre todo el tiempo esperando peticiones. Se despliega en una PaaS de cómputo (Render, Railway).

🗄️ Base de datos

Guarda la información de forma persistente. Se usa una base gestionada (Neon, RDS) para no administrar el motor a mano.

Una vez desplegados, cada uno vive en su propia URL (por ejemplo, el frontend en mi-app.vercel.app y el backend en mi-api.onrender.com) y se comunican por internet. El frontend le pide datos al backend con fetch, y para que el navegador no bloquee esa comunicación entre dos direcciones distintas, el backend debe permitirla explícitamente con una configuración llamada CORS. Es un detalle pequeño que causa muchas dudas la primera vez, así que anótalo.

Al desplegar un backend aparece un problema real: tu aplicación necesita datos sensibles (la conexión a la base de datos, claves de APIs), pero si los escribes en el código y lo subes a GitHub, quedan expuestos para siempre. La solución son las variables de entorno: valores que se configuran en el panel de la plataforma, fuera del código. El programa los lee (por ejemplo, process.env.DATABASE_URL) sin que el valor real aparezca nunca en el repositorio.

Esto tiene una ventaja extra: el mismo código puede funcionar en desarrollo y en producción, simplemente cambiando el valor de las variables en cada entorno. Es una práctica tan estándar que casi todas las plataformas de despliegue tienen una sección dedicada a ellas.

💡 Idea clave: si algo es un secreto (contraseñas, claves, tokens), va en variables de entorno, nunca en el código. Y ojo: en el frontend no hay secretos posibles, porque su código es visible para cualquiera que abra el navegador.

🌐 Actividad 1: Laboratorio — Despliega tu primer frontend en internet

Sube un proyecto frontend sencillo (HTML/CSS/JS) a un repositorio de GitHub. Crea una cuenta gratuita en Vercel o Netlify, conecta el repositorio y despliégalo. Abre la URL pública y verifícala. Luego haz un cambio pequeño, haz commit y push, y observa cómo el sitio se actualiza solo. Responde: ¿por qué se actualizó sin que tocaras la plataforma? ¿qué servicio hay detrás del hosting estático? ¿por qué esto no serviría tal cual para un backend Node.js?

📝 Producto esperado: URL pública del sitio + captura del panel de la plataforma + respuestas a las tres preguntas.

🧠 Actividad 2: Laboratorio — Despliega un backend en la nube

Sube a GitHub una API sencilla (por ejemplo, Node.js + Express con una ruta GET /api/saludo que devuelva un JSON). Crea una cuenta en Render o Railway, crea un "Web Service" conectando el repositorio y configura el comando de inicio (npm start). Si usas datos sensibles, ponlos como variable de entorno. Abre la URL pública seguida de tu ruta. Responde: ¿en qué se diferencia de desplegar el frontend? ¿por qué las variables de entorno son mejores que escribir los datos en el código? ¿qué modelo de servicio (IaaS/PaaS/SaaS) usaste?

📝 Producto esperado: URL pública de la API respondiendo + captura de la respuesta JSON + respuestas escritas.

📐 Actividad 3: Diagrama de arquitectura de despliegue

Dibuja (draw.io o Excalidraw) el diagrama de despliegue de una aplicación completa, indicando en qué servicio concreto desplegarías cada capa: frontend (hosting estático), backend/API (PaaS o cómputo) y base de datos (gestionada). Muestra el flujo de una petición del usuario: frontend → backend → base de datos y la vuelta.

📝 Producto esperado: diagrama exportado como imagen con una breve justificación de cada elección de servicio.

🔎 Actividad 4: Análisis comparativo de plataformas de despliegue

Investiga y compara al menos tres plataformas (Vercel, Netlify, Render, Railway). Para cada una: ¿sirve para frontend, backend o ambos? ¿tiene capa gratuita y con qué límites (horas, suspensión por inactividad)? ¿requiere tarjeta de crédito? ¿se integra con GitHub para despliegue continuo?

📝 Producto esperado: tabla comparativa + recomendación fundamentada de qué usar para el frontend y el backend del proyecto integrador.

🧩 Actividad 5: Cuestionario de comprensión

Responde individualmente: ¿qué significa "desplegar" y en qué se diferencia de ejecutar en localhost? ¿qué es un entorno de producción y por qué separarlo del de desarrollo? ¿por qué frontend y backend se despliegan en servicios distintos (con un ejemplo de cada uno)? ¿qué es el despliegue continuo y qué ventaja aporta? ¿qué son las variables de entorno y por qué importan para la seguridad? ¿qué es CORS y cuándo aparecería?

📝 Producto esperado: respuestas escritas de mínimo 3 líneas por pregunta.
