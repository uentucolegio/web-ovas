🔒 Integración con bases de datos y exposición segura

Tu frontend y tu backend ya viven en internet, cada uno con su dirección. Pero si intentas registrarte o guardar algo, notarás que la información no persiste: falta conectar el "cerebro" (el backend) con su "memoria" (la base de datos). 🧠🔗🗄️ Y una vez conectados, aparece una pregunta que no puede quedar para después: ¿está esto seguro?

Piensa en una tienda física. Ya tienes el local abierto (el despliegue) y el mostrador donde atiendes (la API). Ahora necesitas la bodega donde guardas la mercancía (la base de datos) y, sobre todo, buenas cerraduras: que la bodega no dé a la calle, que la caja no quede abierta y que solo entre quien debe. 🔐 En la nube, esas "cerraduras" se llaman conexiones cifradas, HTTPS, variables de entorno, claves y tokens.

Aquí vas a conectar tu aplicación con una base de datos gestionada de forma segura, entender por qué toda aplicación seria usa HTTPS y aprender a manejar claves y tokens sin exponerlos. Es el paso que convierte un despliegue "de demostración" en una aplicación que de verdad puede tener usuarios. 🚀

✨ Al terminar, tu aplicación guardará datos reales y estará protegida como una de verdad. 🔒

Objetivos de aprendizaje

  • 🔗Integrar una aplicación web desplegada con una base de datos gestionada en la nube, verificando que los datos se guarden y consulten correctamente.
  • 🔐Configurar la exposición segura de la aplicación mediante HTTPS, dominio y un manejo adecuado de claves y tokens.
  • 🛡️Aplicar buenas prácticas de seguridad en la conexión con la base de datos y en el acceso a la API.

Cuando una dirección empieza por https:// y ves el candado 🔒, no es solo un adorno: significa que toda la comunicación entre el navegador y el servidor viaja cifrada mediante un protocolo llamado TLS. Sin HTTPS, todo lo que el usuario escribe (una contraseña, un correo) viaja en texto plano y podría ser leído por cualquiera en el camino; con HTTPS, viaja protegido.

Antes de intercambiar datos, el navegador y el servidor hacen un breve "apretón de manos" (handshake) para ponerse de acuerdo en cómo cifrar. Recórrelo paso a paso y verás que detrás del candado hay un proceso ingenioso. 👇

Una API desplegada está, por definición, abierta a internet. ¿Cómo se controla quién puede usarla? Con dos herramientas que conviene no confundir:

🔑 Clave de API (API key)

Identifica a una aplicación que consume un servicio. Tu backend la envía al llamar a una API externa para que el servicio sepa que es él. Se guarda como variable de entorno.

🎫 Token de autenticación (JWT)

Identifica a un usuario que ya inició sesión. El backend se lo entrega al autenticarse, y el frontend lo envía en cada petición para demostrar quién es, sin reenviar la contraseña.

Una forma sencilla de recordarlo: la clave de API dice "qué app soy", mientras que el token dice "qué usuario soy". Ambos son secretos y ambos deben viajar siempre sobre HTTPS para que nadie los robe en el camino. Y una regla que no falla: los secretos jamás se guardan en el código del frontend, porque cualquiera puede abrir el navegador y leerlo.

Exponer una aplicación de forma responsable se reduce a unas pocas prácticas mínimas, pero críticas:

  • La base de datos nunca se expone directamente a internet: solo el backend se conecta a ella.
  • Todo viaja por HTTPS, incluida la conexión a la base de datos (recuerda el sslmode=require).
  • Los secretos viven en variables de entorno, nunca en el código ni en el repositorio.
  • La API valida todo lo que recibe: nunca confíes en que los datos del frontend son correctos o seguros.
  • CORS se configura de forma restrictiva: solo tu propio frontend puede llamar a tu API.

🔗 Actividad 1: Laboratorio — Conecta tu backend con una base de datos gestionada

En Neon usa (o crea) tu base de datos y copia su cadena de conexión. En el panel de tu backend desplegado (Render/Railway) agrégala como variable de entorno DATABASE_URL (no en el código). En el backend, usa un driver (por ejemplo pg) que lea process.env.DATABASE_URL. Crea una ruta POST que inserte un registro y una GET que devuelva los registros; pruébalas. Responde: ¿dónde quedó la cadena y por qué no en el código? ¿qué significa sslmode=require? Si alguien ve tu código en GitHub, ¿podría conectarse a tu base de datos? ¿por qué?

📝 Producto esperado: capturas de las dos rutas funcionando (inserción y consulta) + respuestas escritas.

🔒 Actividad 2: Laboratorio — Verifica el HTTPS de tu aplicación

Abre tu aplicación desplegada, haz clic en el candado 🔒 de la barra de direcciones y explora el certificado (quién lo emitió, hasta cuándo es válido). Prueba escribir la URL con http:// en vez de https:// y observa qué hace el navegador. Opcional: analiza tu dominio en SSL Labs. Responde: ¿quién emitió tu certificado y tuviste que hacer algo? ¿qué diferencia hay entre http y https para los datos del usuario? ¿por qué hoy es obligatorio HTTPS?

📝 Producto esperado: captura de la información del certificado + respuestas escritas.

🗝️ Actividad 3: Diseño — Inventario de secretos de tu aplicación

Para el proyecto integrador, elabora una tabla con todos los secretos que manejaría tu aplicación (cadena de conexión, clave de alguna API externa, secreto para firmar tokens, etc.). Para cada uno indica: para qué sirve, quién lo necesita (frontend o backend) y dónde debe guardarse. Luego responde: ¿alguno podría ir en el frontend? ¿por qué el frontend es un lugar inseguro para secretos?

📝 Producto esperado: tabla de secretos con su ubicación segura + respuesta justificada.

🕵️ Actividad 4: Análisis de caso — una API mal expuesta

Investiga (o analiza un escenario) de una API o base de datos expuesta de forma insegura: por ejemplo, una API sin HTTPS, una clave filtrada en el código del frontend, o una base de datos accesible desde internet sin restricción. Responde: ¿qué error de exposición se cometió? ¿qué datos o recursos quedaron en riesgo? ¿qué práctica de esta unidad lo habría evitado?

📝 Producto esperado: informe de media página con el análisis y la práctica correcta que lo habría prevenido.

🧩 Actividad 5: Cuestionario de comprensión

Responde individualmente: ¿qué es una cadena de conexión y por qué no debe ir en el código? Explica qué hace HTTPS y por qué importa para una contraseña. ¿Cuál es la diferencia entre una clave de API y un token JWT? ¿Por qué el frontend nunca debe conectarse directo a la base de datos? ¿Qué significa validar las entradas en el backend y por qué no basta con el frontend? ¿Cómo se relacionan las variables de entorno con la seguridad?

📝 Producto esperado: respuestas escritas de mínimo 3 líneas por pregunta.
