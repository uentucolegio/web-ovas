Microservicios y API REST

Microservicios (API REST)

Cuando un sistema crece (por ejemplo, una plataforma de pedidos), se vuelve difícil mantener todo en un solo “bloque” de software. Una forma de organizarlo es separar la solución en servicios pequeños, cada uno responsable de una parte del negocio: usuarios, productos, pedidos, pagos, etc. A esa forma de construir sistemas se le conoce como arquitectura de microservicios.

Para que esos servicios se puedan comunicar, normalmente se exponen como APIs. En esta guía nos enfocamos en el estilo más común: API REST, que usa HTTP (como cuando navegas en internet) y suele intercambiar información en formato JSON. Verás cómo se ubica una API REST en la arquitectura, cómo se diseñan endpoints de manera básica y un ejemplo mínimo de despliegue en contenedor para probar un servicio.

¿Qué es una API REST y por qué es importante?

Una API REST es una forma de exponer funcionalidades de un servicio a través de internet usando HTTP. En REST se trabaja con recursos (por ejemplo, “usuarios” o “productos”). Cada recurso se identifica con una ruta (URL) llamada endpoint.

¿Por qué se usan contenedores (Docker) en microservicios?

En microservicios es común desplegar cada servicio de forma independiente. Para que el despliegue sea repetible, cada servicio se empaca como una imagen y se ejecuta en un contenedor. Esto ayuda a que el servicio se comporte de forma similar en el computador del desarrollador, en pruebas y en servidor.

Un Dockerfile describe cómo se construye la imagen del microservicio. Estructura mínima típica:

FROM python:3.11-slim WORKDIR /app COPY requirements.txt . RUN pip install --no-cache-dir -r requirements.txt COPY . . EXPOSE 8000 CMD ["uvicorn", "main:app", "--host", "0.0.0.0", "--port", "8000"]
Ejemplo práctico mínimo: desplegar y probar una API REST en contenedor

Este ejemplo es “por encima”: la idea es ver una API funcionando, consumir 1–2 endpoints y relacionarlo con la arquitectura (cliente → API). Puedes usar Postman o curl para probar.

Archivos del ejemplo (API mínima con FastAPI)
api-demo/ main.py requirements.txt Dockerfile

main.py (API con 2 endpoints: /salud y /productos):

from fastapi import FastAPI app = FastAPI() PRODUCTOS = [ {"id": 1, "nombre": "Cuaderno"}, {"id": 2, "nombre": "Lapicero"} ] @app.get('/salud') def salud(): return {'estado': 'ok'} @app.get('/productos') def listar_productos(): return PRODUCTOS

requirements.txt:

fastapi uvicorn

Dockerfile:

FROM python:3.11-slim WORKDIR /app COPY requirements.txt . RUN pip install --no-cache-dir -r requirements.txt COPY . . EXPOSE 8000 CMD ["uvicorn", "main:app", "--host", "0.0.0.0", "--port", "8000"]

Cuestionarios o actividades complementarias

Actividad 1. Diseño de endpoints

Propósito: proponer un diseño básico de API REST para un microservicio.

Modalidad: individual.

Instrucciones:

1) Elige un microservicio: Usuarios, Productos o Pedidos.

2) Crea una tabla con mínimo 5 endpoints (acción, método, endpoint, código esperado).

3) Incluye versionado /v1 y usa nombres en plural (ej. /v1/usuarios).

4) Justifica 2 decisiones: por ejemplo, por qué usas GET para consultar y POST para crear.

Evidencia: tabla + justificación.

Actividad 2. Despliegue mínimo de una API en contenedor

Propósito: ver una API REST corriendo y probar endpoints, relacionándolo con la arquitectura.

Modalidad: individual.

Instrucciones:

1) Reproduce el ejemplo ‘api-demo’ (archivos main.py, requirements.txt y Dockerfile).

2) Ejecuta los comandos mínimos: build, run, ps, logs (si aplica), stop y rm.

3) Prueba /salud y /productos (navegador o Postman).

4) Escribe 5–6 líneas: ¿dónde está el servicio (contenedor)? ¿qué hace el puerto publicado? ¿qué devuelve la API?

Evidencia: capturas de pantalla (endpoint + docker ps) + reflexión corta.
