Del modelo Entidad-Relación al modelo relacional 🗄️

En la Unidad 1 te volviste un crack construyendo el modelo entidad-relación: identificaste entidades, atributos, relaciones, cardinalidad, claves y restricciones, y aprendiste a obtener esa información con un buen levantamiento de requerimientos. 💪 Pero aquí va la verdad: ese modelo conceptual todavía no es implementable directamente en un SGBD (Sistema de Gestión de Bases de Datos). Es una representación abstracta, independiente de la tecnología, pensada para facilitar la comunicación entre el equipo técnico y el negocio. Para crear la base de datos dentro de un motor real como MySQL, PostgreSQL o SQL Server, es necesario traducir ese modelo conceptual a un modelo lógico concreto: el modelo relacional. 🔄

El modelo relacional fue propuesto en 1970 por el matemático e investigador Edgar F. Codd, mientras trabajaba en IBM, y representa uno de los aportes más importantes en la historia de la informática. 🏆 Su propuesta fue revolucionaria porque, basándose en la teoría matemática de conjuntos y en la lógica de predicados, permite representar toda la información de una base de datos utilizando una única estructura simple y uniforme: la tabla. Gracias a esta simplicidad y a su sólido fundamento matemático, el modelo relacional se convirtió —y sigue siendo hoy— el estándar dominante en la inmensa mayoría de los SGBD utilizados en la industria del desarrollo de software. 🌍

✨ Al terminar este tema vas a leer cualquier tabla de base de datos como un profesional: tablas, tuplas, atributos y dominios dejarán de ser un misterio para ti. 🚀

Objetivos de aprendizaje

  • 🧠 Explicar los fundamentos del modelo relacional como estándar para la implementación de bases de datos.
  • 🔍 Identificar los elementos que componen una relación: tabla, tupla, atributo y dominio, relacionándolos con los conceptos ya conocidos del modelo entidad-relación.
  • ✅ Aplicar correctamente las propiedades que debe cumplir una relación válida dentro del modelo relacional.
  • 🎯 Definir dominios adecuados para distintos atributos, reconociendo su papel en la validación e integridad de los datos.

Imagina que una tienda online guardara los productos en una hoja, los clientes en un cuaderno y los pedidos en notas del celular... 😵 ¡sería un caos! El modelo relacional lo resuelve con una idea tan simple como poderosa: toda la información de una base de datos se organiza en relaciones —lo que en la práctica llamamos tablas— estructuradas en filas y columnas. Cada tabla guarda datos de un mismo tipo de objeto: todos los estudiantes, todos los productos o todos los pedidos. Y esa uniformidad es su superpoder: no importa qué información se almacene, siempre se representa de la misma manera, lo que simplifica enormemente su gestión, consulta y mantenimiento. 📦

🎵

Piensa en una playlist: la lista es la tabla, cada canción es una fila y cada dato (título, artista, duración) es una columna.

Con base matemática: nace de la teoría de conjuntos y la lógica de predicados (Codd, 1970).

🌍

Una tabla es la estructura que almacena los datos de una relación: las columnas definen qué tipo de información contiene y las filas guardan los valores concretos para cada columna. 📏 Regla de oro: cada tabla debe tener un nombre único dentro de la base de datos, generalmente relacionado con la entidad que representa. Por ejemplo, la entidad ESTUDIANTE del modelo entidad-relación se convierte, en el modelo relacional, en la tabla estudiante.

🧍 La tupla: cada fila es alguien (o algo) del mundo real

Una tupla (fila o registro) es cada una de las ocurrencias individuales almacenadas dentro de una tabla: representa un objeto o evento específico del mundo real. Si la tabla estudiante tiene las columnas id, nombre y correo, la tupla (1, "Juan Pérez", "juan.perez@correo.edu.co") representa a un estudiante concreto. 🎯 Y fíjate en la conexión directa con lo aprendido en la Unidad 1: cada entidad del modelo E-R se convierte en una tabla, y cada ocurrencia de esa entidad se convierte en una tupla.

⚡ El dúo dinámico: esquema vs instancia

El conjunto de todas las columnas de una tabla, con sus nombres y tipos de datos, se conoce como el esquema de la relación y se escribe así: NOMBRE_TABLA(atributo1, atributo2, ..., atributoN). Pero cuidado: no es lo mismo que la instancia. 👇

📐 ESQUEMA = la plantilla

La estructura de la tabla (sus columnas y tipos).

ESTUDIANTE(id, nombre, correo)

🐢 Cambia muy poco en el tiempo.

📸 INSTANCIA = la foto del momento

El conjunto real de tuplas almacenadas.

(1, "Juan Pérez", "juan@...")
(2, "Ana Ruiz", "ana@...")

Un atributo (columna o campo) es cada una de las características que describen a la relación —sí, exactamente el mismo concepto de atributo que ya estudiaste en el modelo E-R—. Cada atributo tiene un nombre único dentro de la tabla y está asociado a un dominio (un conjunto de valores permitidos, que veremos en el siguiente acordeón). 🏷️

⚠️ Aquí nace el primer gran reto del diseño relacional: en el modelo E-R existían atributos compuestos (como dirección, divisible en calle, ciudad y código postal) y atributos multivaluados (como los varios teléfonos de una persona). Pero el modelo relacional exige que cada celda contenga un único valor atómico (indivisible). Esta exigencia se conoce como propiedad de atomicidad. ☝️

🧩 Atributo compuesto

Se descompone en varios atributos simples:

dirección → calle, ciudad, codigo_postal

🔀 Atributo multivaluado

Se resuelve creando una tabla adicional relacionada:

telefonos → tabla aparte (lo veremos con llaves foráneas y normalización)

El dominio de un atributo es el conjunto de todos los valores que ese atributo puede tomar legítimamente. Piensa en él como el portero de una discoteca 🕴️: si un valor no cumple las reglas, simplemente no entra. Definir bien los dominios es una de las decisiones de diseño más importantes del modelo relacional, porque es la primera línea de defensa contra datos inválidos o inconsistentes. 🛡️

Un dominio se define especificando, generalmente, 3 elementos:

1️⃣ Tipo de dato base

Entero, decimal, texto, fecha, booleano...

2️⃣ Rango o conjunto permitido

Ej: entero entre 0 y 5; o la lista cerrada {"M", "F"}.

3️⃣ Formato (opcional)

Ej: un correo debe seguir el patrón texto@texto.dominio.

🏷️ Atributo 🎯 Dominio propuesto
edadNúmero entero entre 0 y 120
estado_pedidoConjunto {"pendiente", "en proceso", "entregado", "cancelado"}
precioNúmero decimal mayor o igual a cero

💡 Dato pro: dos atributos distintos pueden compartir el mismo dominio. Si telefono_cliente y telefono_proveedor usan ambos "texto numérico de 7 a 10 dígitos", tu diseño es consistente en toda la base de datos... y eso te ayuda a detectar errores. 🔍

Cuidado 👀: no cualquier tabla dibujada de forma arbitraria constituye una relación válida en el sentido estricto del modelo relacional. Para que una tabla sea una relación de verdad, debe cumplir estas 6 propiedades:

1️⃣ 🏷️ Nombre de tabla único

Cada tabla tiene un nombre distinto de todas las demás tablas de la base de datos.

2️⃣ ☝️ Valores atómicos

Cada celda contiene un único valor atómico: no se permiten grupos repetitivos ni valores múltiples en una misma celda.

3️⃣ 🏛️ Columnas únicas y del mismo dominio

Cada columna tiene un nombre distinto dentro de la tabla, y todos sus valores provienen del mismo dominio.

4️⃣ ↔️ El orden de las columnas no importa

La información representada es la misma sin importar en qué orden se listen las columnas.

5️⃣ 👯 No hay tuplas idénticas

No pueden existir dos tuplas idénticas dentro de la misma tabla: cada tupla debe ser única.

6️⃣ ↕️ El orden de las tuplas no importa

Una tabla es un conjunto de tuplas y, matemáticamente, los conjuntos no tienen orden intrínseco.
