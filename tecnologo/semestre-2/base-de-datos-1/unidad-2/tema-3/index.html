¿Qué es la integridad referencial?

En el tema anterior aprendiste a conectar tablas mediante claves primarias y foráneas, incluso en el caso más complejo de las relaciones muchos a muchos. Sin embargo, definir una clave foránea es solo el primer paso una vez que la base de datos está en funcionamiento y los usuarios comienzan a insertar, modificar y eliminar información constantemente, surge una pregunta crítica: ¿qué le sucede a los registros relacionados cuando se modifica o se elimina el registro al que hacen referencia?

Imagina, por ejemplo, que en la tabla MATRICULA existe un registro que hace referencia, mediante clave foránea, a un ESTUDIANTE específico. ¿Qué debería ocurrir si alguien intenta eliminar a ese estudiante de la base de datos? ¿Debería el SGBD impedirlo, ya que existen matrículas asociadas? ¿Debería eliminar automáticamente también esas matrículas? ¿Debería, en cambio, dejar la matrícula huérfana, con una referencia a un estudiante que ya no existe? Esta última opción, evidentemente, generaría una inconsistencia grave, tendríamos un registro “fantasma” que hace referencia a algo que ya no está.

La integridad referencial es precisamente el conjunto de reglas y mecanismos que el modelo relacional (y, en la práctica, el propio SGBD) utiliza para evitar este tipo de inconsistencias, garantizando que ninguna clave foránea haga referencia jamás a un valor inexistente. En este tema aprenderás a comprender y aplicar esta restricción con el nivel de detalle necesario para tomar decisiones de diseño informadas.

✨ Cada dato tiene un lugar, y cada relación una responsabilidad: dominar la integridad referencial es aprender a construir sistemas que nunca traicionan la confianza de la información que protegen.🚀

Objetivos de aprendizaje

  • 🧠 Comprender el concepto de integridad referencial y su papel en la consistencia de una base de datos relacional.
  • 💡 Identificar las operaciones (inserción, actualización y eliminación) que pueden poner en riesgo la integridad referencial entre tablas relacionadas
  • 🔧 Reconocer y aplicar las distintas políticas de integridad referencial (RESTRICT, CASCADE, SET NULL, SET DEFAULT) según el contexto del negocio.
  • 📦 Diferenciar la integridad referencial de las demás restricciones de integridad estudiadas previamente (de entidad, de dominio y de unicidad).

🏆 ¡Insignia desbloqueada: GUARDIÁN DE LA INTEGRIDAD!

La integridad referencial es la propiedad que garantiza que toda clave foránea de una tabla, si no es nula, debe coincidir exactamente con un valor existente de la clave primaria en la tabla referenciada. En otras palabras, no puede existir un registro “huérfano” que apunte a un padre inexistente. Es una de las propiedades más importantes que distingue a una base de datos relacional bien diseñada de un simple conjunto de tablas desconectadas entre sí.

Formalmente, dadas dos tablas R (referenciante) y S (referenciada), donde el atributo FK de R es clave foránea que referencia la clave primaria PK de S, la integridad referencial exige que para toda tupla de R, o bien el valor de FK es nulo, o bien existe una tupla en S cuyo valor de PK coincide exactamente con ese valor de FK. Esta definición, aunque parece sencilla, tiene implicaciones profundas sobre cómo deben comportarse las operaciones de modificación de datos, como estudiaremos a continuación.

▶️ Ver recurso

No todas las operaciones sobre una base de datos representan el mismo nivel de riesgo para la integridad referencial. Es importante identificar en cuáles momentos el SGBD debe estar especialmente atento:

  • ➕ Inserción en la tabla referenciante (hija)

    Si se intenta insertar una tupla cuyo valor de clave foránea no existe en la tabla referenciada, la operación debe rechazarse. Por ejemplo, no se debería poder insertar una MATRICULA para un id_estudiante que no existe.

  • ✏️ Actualización de la clave primaria en la tabla referenciada (padre)

    Si se intenta modificar el valor de la clave primaria de un registro que ya está siendo referenciado por otras tablas, es necesario decidir qué ocurre con esas referencias, ya que de lo contrario quedarían apuntando a un valor que ya no existe.

  • 🗑️ Eliminación de un registro en la tabla referenciada (padre)

    Si se intenta eliminar un registro que está siendo referenciado por otras tablas (por ejemplo, eliminar un ESTUDIANTE que todavía tiene MATRÍCULAS asociadas), también es necesario decidir explícitamente qué ocurre con esos registros dependientes.

🎯 Misión 2 · Semáforo de riesgo

¿Qué operación exige una política referencial para no dejar referencias inválidas?

Para resolver de forma explícita qué debe ocurrir cuando se actualiza o elimina un registro referenciado por otras tablas, el modelo relacional (y prácticamente todos los SGBD modernos) ofrece distintas políticas o acciones referenciales, que se definen al momento de crear la clave foránea. Las más utilizadas son:

🚫 RESTRICT (o NO ACTION)

Impide la operación de actualización o eliminación si existen registros dependientes. Es la política más conservadora y, en muchos SGBD, la que se aplica por defecto. Por ejemplo, no se permitiría eliminar un ESTUDIANTE mientras tenga matrículas activas.

🌊 CASCADE

Propaga la operación hacia los registros dependientes: si se elimina el padre, se eliminan los hijos; si se actualiza la clave primaria del padre, se actualiza la clave foránea en todos los hijos. Debe usarse con extremo cuidado, pues una sola eliminación puede borrar grandes cantidades de información relacionada.

⭕ SET NULL

Al eliminar o actualizar el padre, la clave foránea de los hijos se establece en nulo, siempre que la columna lo permita (que no tenga NOT NULL). Es útil cuando la relación es opcional y se desea conservar el hijo “desvinculado” del padre eliminado.

📌 SET DEFAULT

Similar a SET NULL, pero la clave foránea de los hijos se establece en un valor predeterminado previamente definido, en lugar de quedar huérfana o vacía.

🎯 Misión 3 · Elige la política

Una publicación y sus comentarios forman una unidad: al eliminar la publicación también deben eliminarse sus comentarios. ¿Qué política corresponde?

La elección de una política u otra no es una decisión meramente técnica, sino una decisión de negocio. Por ejemplo, en un sistema financiero probablemente se preferirá RESTRICT para evitar eliminar accidentalmente información sensible como transacciones o cuentas; mientras que, en un sistema de blog, podría ser razonable aplicar CASCADE para que, al eliminar una publicación, se eliminen automáticamente todos sus comentarios asociados.

💡 Ejemplo 3: Juego de roles

Divídanse en grupos de cuatro; a cada grupo se le asignará (o elegirá) uno de los siguientes escenarios:

  • (a) Eliminar un CLIENTE que tiene FACTURAS asociadas en un sistema contable.
  • (b) Eliminar una CATEGORÍA de productos en una tienda en línea que todavía tiene productos asociados.
  • (c) Eliminar un AUTOR de un blog que tiene publicaciones asociadas.
  • (d) Eliminar un DEPARTAMENTO de una empresa que todavía tiene empleados asignados.

Cada grupo debe argumentar, ante el resto de la clase, cuál política (RESTRICT, CASCADE, SET NULL o SET DEFAULT) aplicaría a su escenario y por qué, considerando las consecuencias reales para el negocio.
