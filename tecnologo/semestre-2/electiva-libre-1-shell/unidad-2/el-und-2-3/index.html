Permisos, usuarios, grupos y procesos en Linux

La administración de archivos y procesos desde la terminal es una competencia central en el desarrollo web profesional. En entornos reales, el despliegue de aplicaciones, la configuración de servidores, la automatización de tareas y la gestión de servicios ocurren en sistemas Linux remotos, donde el acceso gráfico es limitado o inexistente. Allí, un archivo como .env con credenciales de base de datos o un servicio como nginx dependen por completo de comandos escritos en consola.

Un desarrollador web que desconoce cómo funcionan los permisos, la propiedad de archivos, los usuarios y los procesos en Linux puede exponer credenciales, interrumpir servicios o impedir el correcto funcionamiento de una aplicación en producción. Los comandos chmod, chown, chgrp, useradd, groupadd, ps, kill, systemctl y journalctl son las herramientas con las que se opera con seguridad y precisión en esos escenarios.

🔐 ¡Permisos con criterio! Cada archivo tiene un dueño, un grupo y unas reglas de acceso: entenderlas es la diferencia entre un despliegue seguro y una filtración de credenciales. 🐧💻🛡️

🔐 Permisos en Linux: lectura, escritura y ejecución

🏢
Imagínalo así:

Cada archivo es una oficina con tres juegos de llaves: uno para el propietario, uno para su equipo (el grupo) y uno para cualquier visitante (otros). Cada juego abre tres puertas distintas: mirar (r), modificar (w) y entrar o ejecutar (x).

Linux asigna a cada archivo y directorio un conjunto de permisos que determinan qué acciones puede realizar cada usuario sobre él. Los permisos se dividen en tres categorías: usuario propietario (owner), grupo asociado y resto de usuarios (others). Para cada categoría se definen tres tipos de acceso: lectura (r), escritura (w) y ejecución (x).

El comando ls -l muestra los permisos en una cadena de diez caracteres: el primero indica el tipo de archivo (d para directorio, - para archivo regular) y los nueve siguientes representan los permisos en grupos de tres.

$ ls -l
drwxr-xr-x 5 deploy deploy 4096 jul 20 10:15 mi-proyecto-web
-rw-r--r-- 1 deploy deploy  256 jul 20 10:15 .env
-rwxr-xr-x 1 deploy deploy 1024 jul 20 10:15 server.js
  • mi-proyecto-web es un directorio (d) con rwxr-xr-x: el propietario lee, escribe y entra; el grupo y otros solo leen y entran.
  • .env tiene rw-r--r--: solo el propietario puede escribir, pero todos pueden leerlo (un riesgo si contiene credenciales).
  • server.js es ejecutable (rwxr-xr-x), por lo que puede invocarse directamente como script.

🔢 Notación numérica de permisos

Cada tipo de acceso tiene un valor: lectura = 4, escritura = 2, ejecución = 1. La suma por categoría produce un número de tres dígitos (propietario, grupo, otros). Haz clic en cada fila para resaltarla:

🔢 Número 🔤 Equivalente 📄 Uso típico en un proyecto web
755 rwxr-xr-x Directorios públicos y scripts ejecutables (public/)
750 rwxr-x--- Código fuente accesible solo para el propietario y su equipo (src/)
644 rw-r--r-- Archivos estáticos que el servidor debe leer (index.html)
640 rw-r----- Logs legibles por el equipo, invisibles para el resto (logs/app.log)
600 rw------- Credenciales y variables sensibles (.env)

📌 En los directorios, el permiso x no significa “ejecutar”, sino poder entrar y atravesar la carpeta. Sin x en un directorio, no puedes acceder a los archivos que hay dentro aunque tengan permiso de lectura.

👥 Usuarios y grupos

Linux es un sistema multiusuario: varios usuarios pueden acceder al mismo sistema con identidades y privilegios distintos. Cada usuario tiene un identificador único (UID) y pertenece a un grupo principal, además de poder formar parte de grupos adicionales.

Los grupos permiten administrar permisos de manera colectiva: al asignar permisos a un grupo, todos sus miembros heredan esos accesos sin necesidad de configurar cada usuario individualmente. Es la forma habitual de dar acceso a un equipo de desarrollo sobre la carpeta de un proyecto.

⌨️ Comandos de gestión de usuarios y grupos

Haz clic en cada fila para resaltarla:

⌨️ Comando 📄 Qué hace
useradd Crea un nuevo usuario en el sistema
passwd Define o cambia la contraseña de un usuario
groupadd Crea un nuevo grupo
usermod -aG Agrega un usuario a un grupo sin borrar sus grupos actuales
groupdel Elimina un grupo
groups o id Muestra los grupos a los que pertenece un usuario
Ejemplo aplicado — crear un usuario y un equipo de desarrollo

Se crea el usuario frontend-dev con directorio home (-m), /bin/bash como shell (-s) y un comentario descriptivo (-c). Luego se crea el grupo dev-team y se agrega al usuario:

$ sudo useradd -m -s /bin/bash -c "Desarrollador Frontend" frontend-dev
$ sudo passwd frontend-dev
$ sudo groupadd dev-team
$ sudo usermod -aG dev-team frontend-dev
$ groups frontend-dev
# El grupo dev-team se usará después para asignar permisos
# compartidos sobre los directorios del proyecto.

⚖️ Usuario de persona vs. usuario de servicio

Usuario interactivo
$ sudo useradd -m -s /bin/bash frontend-dev

Tiene carpeta personal y shell: una persona puede iniciar sesión, editar código y ejecutar comandos. Pensado para miembros del equipo.

VS
Usuario de servicio
$ sudo useradd -r -s /usr/sbin/nologin -d /var/lib/mi-app-web mi-app-user

-r crea una cuenta de sistema (UID bajo 1000), -s /usr/sbin/nologin impide iniciar sesión y -d fija su directorio. Reduce el impacto si el servicio se ve comprometido.

🖥️ En producción, servicios como Nginx, Node.js o PostgreSQL se ejecutan bajo usuarios dedicados sin inicio de sesión interactivo. Nunca ejecutes una aplicación web como root.

🛠️ Cambiar permisos y propiedad: chmod, chown y chgrp

chmod (change mode) modifica los permisos de acceso de archivos y directorios. Admite notación numérica (por ejemplo, 755) o simbólica (por ejemplo, u+x, g-w). La opción -R aplica los cambios de forma recursiva a un directorio y todo su contenido.

Sintaxis básica:

$ chmod [opciones] permisos archivo_o_directorio

Ajuste típico de permisos en un proyecto web:

$ chmod 755 public/
$ chmod 644 public/index.html
$ chmod 600 .env
# public/ navegable por todos, index.html legible por todos,
# .env protegido contra lecturas no autorizadas.

chmod Comando
-R Opción
750 Permisos
src/ Objetivo

👑 Cambiar propietario y grupo: chown y chgrp

chown (change owner) modifica el usuario y/o el grupo propietario de un archivo o directorio; chgrp cambia únicamente el grupo.

$ chown [opciones] usuario:grupo archivo_o_directorio
$ sudo chown -R www-data:www-data /var/www/mi-proyecto-web
# Asigna recursivamente el usuario y grupo www-data (habitual en
# Nginx/Apache) para que el servidor pueda servir los archivos.
$ sudo chgrp -R dev-team ~/proyectos/mi-api-node
# Solo cambia el grupo: el propietario se mantiene.

⚠️ Niveles de riesgo al asignar permisos

chmod 600 .env → Solo el propietario lee y escribe: lo correcto para credenciales
chmod 644 index.html → Legible por todos: adecuado para archivos públicos, nunca para secretos
chmod -R 777 /var/www → Escritura y ejecución para cualquiera: riesgo alto de manipulación
sudo chmod -R 777 / → ⚠️ PELIGROSO: deja todo el sistema abierto e inutilizable
⚠️ Errores comunes y cómo evitarlos:
  • Aplicar 777 a directorios completos “para que funcione”. Usa 755 en directorios y 644 en archivos.
  • Olvidar el permiso x en directorios: sin él no se puede atravesar la ruta, aunque los archivos sean legibles.
  • Usar usermod -G sin -a: reemplaza todos los grupos suplementarios del usuario. Usa siempre usermod -aG.
Ejemplo integrado — permisos de un proyecto Node.js

Estructura típica y permisos ajustados según la naturaleza de cada recurso:

$ mkdir -p ~/proyectos/mi-api-node/{src,public,logs}
$ cd ~/proyectos/mi-api-node
$ touch .env logs/app.log
$ sudo chown -R $USER:dev-team .
$ chmod 750 src
$ chmod 755 public
$ chmod 640 logs/app.log
$ chmod 600 .env
  • src (750): limitado al propietario y al equipo.
  • public (755): lectura y acceso general, escritura solo del propietario.
  • logs/app.log (640) y .env (600): restringidos.

⚙️ Procesos y servicios

🎛️
La clave conceptual:

Un proceso es una instancia en ejecución de un programa: un servidor web, una base de datos, un script en segundo plano. Un servicio es un proceso que el sistema mantiene funcionando de forma continua y persistente, incluso tras reiniciar el servidor.

🔎 Inspeccionar procesos

Haz clic en cada fila para resaltarla:

⌨️ Comando 📄 Qué muestra
ps Una instantánea de los procesos en ejecución
ps aux | grep node Filtra los procesos relacionados con Node.js y muestra su PID
top o htop Vista dinámica en tiempo real de CPU, memoria y recursos por proceso
kill Envía señales a un proceso para terminarlo o cambiar su comportamiento

Flujo habitual para localizar y revisar un proceso de una aplicación web:

$ ps aux | grep node
deploy   4821  0.4  1.2 node server.js
$ top
# El PID (4821) identifica al proceso: es el dato que
# necesitarás para detenerlo con kill.

⚖️ Detener procesos de forma segura

kill -15 (SIGTERM) — primero
$ kill -15 4821

Pide al proceso que termine de forma ordenada: cierra conexiones, guarda estado y libera recursos. Es la opción por defecto y la recomendada.

VS
kill -9 (SIGKILL) — último recurso
$ kill -9 4821

Fuerza la terminación inmediata. El proceso no puede limpiar nada: puede dejar archivos bloqueados o datos a medio escribir. Úsalo solo si no responde.

🧩 Gestión de servicios con systemd

La mayoría de distribuciones modernas usan systemd como sistema de inicialización. El comando systemctl controla los servicios:

⌨️ Comando 📄 Efecto
systemctl status nginx Consulta el estado actual del servicio y sus últimas líneas de log
sudo systemctl start nginx Inicia el servicio en ese momento
sudo systemctl stop nginx Detiene el servicio
sudo systemctl restart nginx Reinicia el servicio, útil tras cambiar su configuración
sudo systemctl enable nginx Hace que el servicio arranque automáticamente al iniciar el sistema
Consultar logs con journalctl

journalctl consulta los registros del sistema y de los servicios gestionados por systemd. Es la herramienta clave para diagnosticar por qué un servicio no arranca:

$ journalctl -u nginx -n 50
# Últimas 50 líneas de log del servicio nginx.
$ journalctl -f -u mi-app-web
# Sigue en tiempo real los logs de un servicio personalizado.
💡 Secuencia de diagnóstico recomendada: systemctl status para ver qué ocurre → journalctl -u servicio para leer el error concreto → corregir la configuración → systemctl restart para aplicar el cambio.
