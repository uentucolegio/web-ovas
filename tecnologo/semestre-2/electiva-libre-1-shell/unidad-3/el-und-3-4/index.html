Prompting técnico, verificación y registro de comandos generados con IA

Las herramientas de inteligencia artificial, como ChatGPT, Claude, Gemini y GitHub Copilot, pueden ayudarte a crear comandos de Linux y scripts de Bash rápidamente. Sin embargo, sus respuestas pueden contener errores o instrucciones que afecten los archivos y la seguridad de un servidor.

Por eso, no basta con copiar y ejecutar un comando: es necesario entenderlo y verificarlo antes de usarlo. Un error en una instrucción puede borrar archivos importantes o modificar permisos de forma insegura. En esta guía aprenderás a formular solicitudes claras a la IA, verificar los comandos generados y registrar los resultados para trabajar de forma segura y organizada.

¡Confía, pero verifica! Un buen prompt reduce las suposiciones de la IA, la lectura crítica detecta los riesgos antes de ejecutar y el registro deja evidencia de lo que hiciste.

Objetivos de aprendizaje

  • Redactar prompts técnicos que especifiquen sistema operativo, shell, rutas reales, restricciones de seguridad y formato de respuesta para obtener comandos y scripts de Bash precisos.
  • Identificar en un comando o script generado por IA los patrones de riesgo más frecuentes: operaciones destructivas, permisos excesivos, variables sin comillas, opciones inexistentes y diferencias entre GNU y BSD.
  • Verificar comandos antes de ejecutarlos mediante man, --help, type, bash -n, shellcheck, modos de simulación y trazas con set -x, dentro de un entorno de prueba aislado.
  • Registrar de forma auditable el proceso de trabajo con IA usando history con marcas de tiempo, script, tee y una bitácora versionada.

Prompting técnico, verificación y registro de comandos con IA

Aprende a pedir comandos a la IA con precisión, a revisarlos críticamente antes de ejecutarlos y a dejar evidencia auditable de tu trabajo con history, script, tee y una bitácora.

Tema 1 de 5

Prompting técnico

Imagínalo así

Pedir un comando a la IA es como pedir indicaciones a alguien que no conoce tu ciudad: si no le dices dónde estás ni a dónde vas, te dará una ruta basada en suposiciones. Mientras más datos reales entregues, más exacta será la ruta.

Un prompt es la instrucción en lenguaje natural que se entrega a un modelo de IA. En el trabajo con terminal, el prompt técnico es aquel que reduce la ambigüedad al mínimo: el modelo solo dispone de la información escrita en la solicitud, de modo que todo dato omitido (distribución, versión de una herramienta, ruta real, si el comando correrá con sudo) será completado con una suposición. La calidad del comando obtenido depende directamente de cuántas de esas suposiciones se eliminan.

Un prompt débil frente a un prompt técnico

Para la misma tarea, un prompt débil como «dame un comando para subir mi página al servidor» obliga al modelo a suponer la herramienta, el origen, el destino y el sistema: la respuesta puede ser scp, rsync, ftp o un flujo con Docker, y ninguno ajustado al proyecto real. Compara:

Prompt débil
prompt
# una sola línea, sin datos dame un comando para subir mi página al servidor

Sin entorno, sin rutas y sin restricciones: todo es suposición.

Prompt técnico
prompt
Entorno: Ubuntu 24.04, Bash 5.2, GNU rsync 3.2.7. Sin sudo. Contexto: React con Vite en ~/proyectos/portafolio-react. npm run build genera dist/. El sitio está en /var/www/portafolio y tiene uploads/ con imágenes de usuarios. Objetivo: script deploy.sh que copie dist/ a /var/www/portafolio, elimine archivos obsoletos y conserve uploads/. Restricciones: sin chmod 777 ni rm -rf; modo de simulación; validar que dist/ exista antes de copiar. Formato: script comentado con set -euo pipefail y una tabla con cada opción de rsync y su función.

Cada línea cumple una función: el entorno fija la sintaxis (GNU y no BSD, Bash y no Zsh); el contexto entrega rutas reales en lugar de marcadores como /ruta/a/tu/proyecto; la restricción sobre uploads/ obliga al modelo a resolver la exclusión; el modo de simulación facilita la verificación posterior, y pedir la tabla de opciones obliga a que la respuesta sea revisable punto por punto.

Prácticas complementarias

  • Pedir la explicación de cada opción, no solo el comando. Una explicación incoherente con la documentación es señal de una opción inventada.
  • Entregar la salida real de los errores. Si el comando falla, se pega el mensaje exacto de la terminal (por ejemplo, rsync: [Receiver] mkdir "/var/www/portafolio" failed: Permission denied (13)) en lugar de escribir «no funcionó».
  • Iterar sobre la misma conversación para corregir, en lugar de iniciar una nueva sin contexto.
  • Pedir alternativas más seguras cuando la respuesta incluye sudo, rm -rf o cambios de permisos recursivos.
Errores comunes: pegar en el prompt el contenido de un archivo .env, llaves SSH o tokens de API. Los datos sensibles se reemplazan por valores ficticios (DB_PASSWORD=<oculto>) antes de enviarlos a cualquier servicio externo. También es frecuente aceptar rutas de marcador de posición (/path/to/project) y ejecutarlas sin reemplazarlas.

Lectura crítica: patrones de riesgo

Imagínalo así

Revisar un comando generado por IA es como leer la letra pequeña de un contrato antes de firmarlo: si no lo lees completo, puedes aceptar condiciones que no querías.

La primera verificación se hace sin ejecutar nada: consiste en leer el comando completo y localizar las construcciones que pueden causar daños irreversibles o comportamientos inesperados. Los modelos de IA reproducen patrones frecuentes en foros y repositorios públicos, incluidos los malos. Estos aparecen con regularidad en respuestas generadas:

Las opciones inventadas también son un riesgo

Los modelos pueden generar opciones con nombres verosímiles que no existen, como rsync --backup-dated. Toda opción que no se haya usado antes se comprueba en la documentación del sistema, que es el tema de la siguiente pestaña.

GNU

Sintaxis de Linux. El prompt debe indicar «GNU» cuando el servidor es Ubuntu o Debian.

BSD

Sintaxis de macOS. Un comando pensado para BSD puede fallar o actuar distinto en Linux.

Regla de oro: si no puedes explicar con tus palabras qué hace cada parte de un comando, todavía no estás listo para ejecutarlo.

Documentación y validación de sintaxis

Consultar la documentación del sistema

La fuente autorizada sobre lo que hace un comando es la documentación instalada en el propio sistema, porque corresponde exactamente a la versión que se va a ejecutar. Linux ofrece varias herramientas para consultarla:

Comando Función Cuándo usarlo
man rsyncAbre el manual completo (manual page)Para leer la descripción detallada de una opción
rsync --helpResumen breve de opcionesPara una consulta rápida, combinado con grep
man -k compressBusca en las descripciones de todos los manualesCuando no se sabe qué comando cumple una función
type llIndica si un nombre es un programa, un alias, una función o un comando interno de BashCuando un comando se comporta distinto a lo esperado
which nodeMuestra la ruta del ejecutable que se usaráPara confirmar qué versión de un programa está en el PATH
rsync --versionVersión instaladaPara comparar con la versión indicada en el prompt

Dentro de man, la tecla / abre una búsqueda: escribir /--delete y pulsar Enter salta a la primera aparición, n avanza a la siguiente y q sale del manual. Con --help, la búsqueda se hace mediante una tubería:

Terminal — bash
usuario@equipo:~$ rsync --help | grep -- '--delete' usuario@equipo:~$ rsync --help | grep -- '--backup-dated' || echo "La opción no existe en esta versión"

El doble guion -- después de grep indica que lo siguiente es el patrón de búsqueda y no una opción de grep; sin él, grep interpretaría --delete como una opción propia. En la segunda línea, si grep no encuentra coincidencias devuelve un código de salida distinto de cero y se ejecuta el echo posterior a ||.

Validación de sintaxis: bash -n y ShellCheck

Antes de ejecutar un script generado se comprueba que su sintaxis sea válida y que no contenga errores conocidos.

bash -n

Lee el script completo y reporta errores de sintaxis (un if sin fi, comillas sin cerrar) sin ejecutar ninguna línea. Si no imprime nada, la sintaxis es válida, lo que no garantiza que el script haga lo correcto.

ShellCheck

Analizador estático de scripts de shell: detecta variables sin comillas, comparaciones mal escritas y comandos peligrosos. Se instala con sudo apt install shellcheck y existe como extensión de VS Code.

SC2086

Cada advertencia tiene un código que puede consultarse en la wiki del proyecto para conocer la causa y la corrección.

El siguiente script fue generado por un asistente a partir del prompt «script para recompilar mi tienda y apuntar a la API de producción». Las líneas marcadas en rosa son las problemáticas:

script generado por IA
1 #!/bin/bash 2 BUILD_DIR=~/proyectos/tienda-web/dist 3 rm -rf $BUILD_DIR/* 4 npm run build --prefix ~/proyectos/tienda-web 5 sed -i '' 's/localhost:3000/api.tienda-web.co/' ~/proyectos/tienda-web/.env.production 6 chmod -R 777 $BUILD_DIR
Diagnóstico
  • bash -n no reporta ningún error, porque la sintaxis es válida.
  • ShellCheck señala SC2115 en la línea 3: si BUILD_DIR llegara vacía, la orden se convertiría en rm -rf /*. Si la ruta se recibiera como argumento (BUILD_DIR=$1), también marcaría SC2086 por usar la variable sin comillas.
  • La línea 5 usa la sintaxis de sed de macOS: en Linux toma '' como el patrón y la expresión de reemplazo como un nombre de archivo (sed: can't read s/localhost:3000/...: No such file or directory).
  • La línea 6 asigna permisos 777 que no son necesarios para servir archivos estáticos.
Ninguna de las herramientas por sí sola encuentra todos los problemas; se complementan: la lectura crítica, la documentación, bash -n y ShellCheck.

Ejecución controlada: simulación, trazas y aislamiento

Imagínalo así

Es como el ensayo general de una obra: se practica en un escenario de prueba antes de presentarla ante el público. En el escenario de prueba, un error no cuesta nada.

Simulación (dry run)

Una vez revisado el código, el siguiente paso es observar qué haría el comando sin que lo haga. Muchas herramientas incluyen un modo de simulación que reporta las acciones previstas sin modificar nada:

Herramienta Simulación Ejecución real
rsyncrsync -avn --delete dist/ /var/www/portafolio/La misma orden sin -n
findfind logs/ -name '*.log' -mtime +7 -printReemplazar -print por -delete
git cleangit clean -ndgit clean -fd
sedsed 's/localhost/api.tienda-web.co/' .env.production (imprime el resultado)Agregar -i para modificar el archivo
apt-getapt-get -s install nginxSin -s, con sudo
rm, mv, cp-i pide confirmación por cada archivoSin -i

Cuando la herramienta no tiene modo de simulación, se antepone echo al comando destructivo para imprimirlo en lugar de ejecutarlo: echo rm -rf "$BUILD_DIR"/* muestra la lista exacta de rutas que se eliminarían, con las variables y patrones ya expandidos.

Trazas con bash -x y set -x

Para observar un script mientras se ejecuta se usa la traza de Bash. bash -x deploy.sh, o la línea set -x dentro del script, imprime cada orden antes de ejecutarla, precedida de + y con las variables ya reemplazadas por sus valores:

Terminal — bash
+ BUILD_DIR=/home/estudiante/proyectos/tienda-web/dist + '[' -d /home/estudiante/proyectos/tienda-web/dist ']' + rsync -avn --delete /home/estudiante/proyectos/tienda-web/dist/ /home/estudiante/practica-u3/srv/www/tienda/

Esta salida permite confirmar que cada ruta es la esperada antes de quitar el modo de simulación. La traza se desactiva con set +x.

Entornos de prueba aislados

Ningún comando generado por IA se prueba por primera vez sobre datos reales. Existen tres niveles de aislamiento, de menor a mayor:

  1. Copia de práctica. Se replica la estructura en una carpeta de prueba (por ejemplo ~/practica-u3/srv/www/tienda) con cp -a, que conserva permisos y fechas, y se ajustan las rutas del script para apuntar a ella.
  2. Punto de restauración con Git. En un proyecto versionado se confirma que git status esté limpio antes de ejecutar el comando; si el resultado no es el esperado, git diff muestra los cambios y git restore . los revierte.
  3. Contenedor desechable. Con Docker instalado, docker run --rm -it -v "$PWD":/work -w /work ubuntu:24.04 bash abre una terminal en un Ubuntu limpio con la carpeta actual montada en /work; --rm elimina el contenedor al salir. Es útil para probar instalaciones con apt sin alterar el sistema propio.
Errores comunes: probar en la copia y luego ejecutar sobre producción un script distinto al probado, por ejemplo tras «un último ajuste» pedido a la IA. Cualquier cambio en el script reinicia el ciclo de verificación.

Registro del trabajo con IA

Historial de comandos con marcas de tiempo

history es un comando interno de Bash que lista las órdenes ejecutadas en la terminal, numeradas en orden. Bash guarda el historial en memoria durante la sesión y lo escribe en el archivo ~/.bash_history al cerrarla. Por defecto no registra la fecha ni la hora, un dato indispensable para reconstruir qué se hizo y cuándo; la variable HISTTIMEFORMAT lo activa.

Terminal — bash
usuario@equipo:~$ export HISTTIMEFORMAT='%F %T ' usuario@equipo:~$ history 5 usuario@equipo:~$ history | grep rsync usuario@equipo:~$ history -a
  • La primera línea define el formato de fecha (el mismo de date); para que sea permanente se agrega al final de ~/.bashrc.
  • La segunda muestra las cinco órdenes más recientes, ahora con fecha y hora.
  • La tercera filtra solo las órdenes que contienen rsync.
  • La cuarta escribe de inmediato en ~/.bash_history las órdenes de la sesión actual, sin esperar a cerrar la terminal.
En Ubuntu, HISTCONTROL=ignoreboth viene activada en ~/.bashrc: las órdenes que empiezan con un espacio no se guardan en el historial. Sirve para evitar que un token o una contraseña quede registrada, pero también explica por qué a veces una orden «no aparece».

Grabación de sesiones con script

script graba en un archivo todo lo que aparece en la pantalla de la terminal, desde que se inicia hasta que se termina con exit.

Uso Función
script ~/practica-u3/registros/sesion.logInicia la grabación y sobrescribe el archivo si existe
script -a archivo.logAgrega al final del archivo (append)
script -q archivo.logOmite los mensajes de inicio y fin de grabación
exit o Ctrl+DTermina la grabación
less -R archivo.logMuestra el archivo interpretando los códigos de color
Errores comunes: olvidar el exit y seguir trabajando dentro de la grabación, o grabar una sesión en la que se muestra el contenido de .env o se escribe una contraseña. El archivo de script guarda exactamente lo que aparece en pantalla.

Registro de ejecuciones con tee

Para conservar solo la salida de un script concreto, sin grabar toda la sesión, se usa tee, que copia lo que recibe por la entrada estándar tanto a la pantalla como a un archivo. Combinado con la traza de Bash y la redirección de errores produce un registro completo de una ejecución:

Terminal — bash
usuario@equipo:~$ bash -x scripts/deploy.sh 2>&1 | tee -a registros/deploy_$(date +%F).log

bash -x genera la traza de cada orden; esa traza se escribe en la salida de errores, por lo que 2>&1 la une a la salida estándar para que ambas pasen por la tubería. tee -a muestra todo en la terminal y lo agrega al log del día, cuyo nombre incluye la fecha gracias a la sustitución de comandos.

Bitácora de uso de IA y control de versiones

Los registros anteriores muestran qué se ejecutó, pero no por qué ni de dónde salió. La bitácora es un archivo en Markdown, por ejemplo docs/registro-ia.md dentro del repositorio, donde cada entrada documenta un uso de IA con campos fijos. Su propósito es que otro integrante del equipo, o el mismo autor semanas después, pueda entender y reproducir la decisión.

docs/registro-ia.md
## 2026-09-30 — Script de despliegue del portafolio - **Asistente:** Claude (chat web) - **Prompt:** ver `docs/prompts/deploy-portafolio.txt` - **Archivo resultante:** `scripts/deploy.sh` - **Verificación:** - `bash -n` sin errores; ShellCheck: SC2115 en línea 12 (corregido con `${DESTINO:?}`) - `rsync --help`: confirmadas `-a`, `-v`, `-n`, `--delete`, `--exclude` - Simulación con `-n` sobre `~/practica-u3/srv/www/portafolio`: `uploads/` no se ve afectada - **Cambios respecto a la respuesta original:** se eliminó `chmod -R 777`; se agregó validación de `dist/` - **Evidencia:** `registros/deploy_2026-09-30.log` - **Resultado:** desplegado sin errores

Además de la bitácora, el propio script indica su procedencia mediante un comentario de cabecera, de modo que la información viaja con el archivo:

scripts/deploy.sh
#!/usr/bin/env bash # deploy.sh — Publica dist/ en /var/www/portafolio conservando uploads/ # Origen: generado con asistente de IA el 2026-09-30 y revisado manualmente. # Verificación y cambios: docs/registro-ia.md (entrada 2026-09-30) set -euo pipefail

Finalmente, el script, el prompt y la bitácora se versionan juntos con Git en un mismo commit, para que el historial del repositorio muestre que el código y su verificación llegaron a la vez:

Terminal — bash
usuario@equipo:~$ git add scripts/deploy.sh docs/registro-ia.md docs/prompts/deploy-portafolio.txt usuario@equipo:~$ git commit -m "feat(scripts): agrega deploy.sh generado con IA y verificado"
Errores comunes: versionar los archivos de script o los logs de ejecución cuando contienen rutas internas, nombres de usuario o variables de entorno. Lo recomendable es agregar la carpeta registros/ al archivo .gitignore y versionar solo la bitácora, que resume la evidencia sin exponer datos sensibles.
Ciclo completo: prompt técnico · lectura crítica · documentación · bash -n y ShellCheck · simulación y traza · entorno aislado · registro (history, script, tee) · bitácora y commit.
