Principios SOLID introductorios 🚀

Un sistema de pedidos calcula descuentos, genera comprobantes y envía mensajes. Al cambiar el formato del comprobante también deja de funcionar el cálculo. El problema puede ser de diseño: varias decisiones que cambian por motivos diferentes quedaron mezcladas en una clase.

SOLID reúne cinco principios para razonar sobre esas dependencias. No obliga a crear muchas interfaces: busca facilitar cambios previsibles sin dañar contratos existentes. Se presupone conocimiento de clases, encapsulación, interfaces y polimorfismo. El caso conductor será un cálculo de pedidos en memoria.

La base es Java 17 y no requiere marcos de inyección ni bases de datos. La mejora se evaluará mediante cambios concretos y resultados observables. La meta es explicar por qué una responsabilidad pertenece a un componente y qué compromisos debe respetar al colaborar.

🎮 Reto de 10 puntos: ¿Qué separación permite probar el importe sin conectarse al correo?

El consumidor trabaja con Politica. Una reducción fija se incorpora como implementación; la selección se realiza al ensamblar el programa. OCP protege una variación identificada, no prohíbe corregir código.

🎮 Reto de 10 puntos: ¿Dónde eliges una nueva política sin reescribir el cálculo?

Contrato: un subtotal no negativo produce un total entre cero y el subtotal. Dos promociones pueden dar importes diferentes y ser sustituibles. Una que exige subtotal positivo rompe la promesa para cero.

🎮 Reto de 10 puntos: ¿Qué resultado rompe el contrato para subtotal 300?

Un cliente que imprime no necesita guardar en la nube. Una interfaz pequeña debe responder al uso. Inyectar Politica por constructor o parámetro permite que el cálculo dependa del contrato; inyectar una clase concreta no prueba DIP.

public class DemoSolid {
    interface Politica {
        // Para subtotal >= 0, devuelve entre 0 y subtotal.
        int aplicar(int subtotal);
    }
    static class SinDescuento implements Politica {
        public int aplicar(int subtotal) { return subtotal; }
    }
    static class DiezPorCiento implements Politica {
        public int aplicar(int subtotal) {
            return subtotal - subtotal / 10;
        }
    }
    static int total(int subtotal, Politica politica) {
        if (subtotal < 0 || politica == null) {
            throw new IllegalArgumentException("Entrada invalida");
        }
        int valor = politica.aplicar(subtotal);
        if (valor < 0 || valor > subtotal) {
            throw new IllegalStateException("Contrato incumplido");
        }
        return valor;
    }
    public static void main(String[] args) {
        System.out.println(total(10000, new SinDescuento()));
        System.out.println(total(10000, new DiezPorCiento()));
        System.out.println(total(0, new DiezPorCiento()));
        try {
            total(-1, new SinDescuento());
        } catch (IllegalArgumentException e) {
            System.out.println("Rechazado");
        }
    }
}

    4. Casos para decidir
    1. Pago con doble responsabilidad
    Un cambio de correo obliga a modificar el cálculo. La solución es separar las razones de cambio, manteniendo una operación clara de ensamblaje.
    ¿Qué prueba debería poder hacerse sin correo?
    2. Abstracción excesiva
    Un valor constante de IVA no requiere por sí solo diez fábricas. La separación debe justificarse con un cambio concreto, no con cantidad de patrones.
    ¿Qué justifica una nueva interfaz?
    3. Contrato monetario
    Para subtotal 999 la política devuelve 900: 999 / 10 es 99 y se resta ese descuento. Otra política de redondeo sería un cambio del contrato.
    ¿Cuál es el descuento entero aplicado?
