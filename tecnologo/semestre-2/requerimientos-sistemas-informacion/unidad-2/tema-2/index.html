Historias de Usuario y Criterios de Aceptación

Imagina que estás construyendo una casa 🏠. El arquitecto no te entrega planos técnicos complejos, sino que te dice: "Como futuro dueño, quiero una cocina espaciosa para poder cocinar para mi familia". ¡Eso es una historia de usuario! Es una forma simple y directa de expresar una necesidad desde la perspectiva de quien la va a usar.

En el desarrollo de software ágil, las historias de usuario son exactamente eso: descripciones breves de funcionalidades contadas desde el punto de vista del usuario final. No son documentos técnicos aburridos, sino conversaciones vivas que capturan qué necesita el usuario y por qué lo necesita 💬.

Pero una historia de usuario no es suficiente por sí sola. Necesitamos saber cómo vamos a verificar que se cumplió correctamente. Ahí entran los criterios de aceptación, que son como las reglas del juego: condiciones claras que nos dicen cuándo una historia está "terminada" y lista para entregar ✅.

✨ En este OVA aprenderás a transformar necesidades vagas en historias de usuario claras, aplicar los principios INVEST para evaluar su calidad, y definir criterios de aceptación verificables. ¡Prepárate para escribir historias que realmente importan! 🚀

Objetivos de aprendizaje

  • 🎯 Comprender qué son las historias de usuario y su importancia en el desarrollo ágil de software como herramienta para capturar necesidades del usuario.
  • 📝 Aplicar el modelo de las 3 C (Tarjeta, Conversación, Confirmación) para estructurar historias de usuario efectivas y colaborativas.
  • ⚖️ Utilizar la lista de comprobación INVEST para evaluar y mejorar la calidad de las historias de usuario.
  • ✅ Definir criterios de aceptación verificables utilizando formatos de lista de reglas y escenarios Dado-Cuando-Entonces.
  • 🔗 Establecer la cadena de trazabilidad mínima que conecta objetivos, necesidades, historias, criterios y pruebas.

Todo comienza con una necesidad. Alguien tiene un problema, una oportunidad, o una idea de mejora. Pero esa necesidad expresada en lenguaje natural suele ser vaga: "Quiero que el sistema sea más rápido", "Necesito mejor reportes", "La aplicación debería ser más fácil de usar". 😕

El desafío es transformar esa necesidad en algo verificable: una descripción clara que podamos probar y validar. Las historias de usuario son el puente entre lo que el usuario quiere y lo que el equipo puede construir 🌉.

💡 Dato curioso

Según el CHAOS Report del Standish Group, el 31% de los proyectos fallan por requerimientos poco claros. Las historias de usuario bien escritas reducen significativamente este riesgo al hacer las necesidades explícitas y compartidas.

🎮 Misión 1: Identifica el tipo (necesidad vs historia)

Puntos: 0/3

Ron Jeffries, uno de los pioneros de XP (Extreme Programming), propuso el modelo de las 3 C para entender qué es realmente una historia de usuario. No es un documento estático, sino un proceso vivo de comunicación 🔄.

📇 TARJETA (Card)

Recordatorio breve de la necesidad. Es la frase escrita: "Como [rol], quiero [acción], para [beneficio]".

No contiene todos los detalles, solo lo suficiente para iniciar la conversación.

💬 CONVERSACIÓN (Conversation)

Discusión entre el equipo, el Product Owner y los usuarios para explorar detalles.

Aquí se aclaran dudas, se negocian detalles y se construye entendimiento compartido.

✅ CONFIRMACIÓN (Confirmation)

Criterios de aceptación y pruebas que demuestran valor.

Define qué significa "terminado" y cómo vamos a verificar que se cumplió.

⚠️ Error común

Muchos equipos escriben la tarjeta y piensan que terminaron. ¡Error! La tarjeta es solo el 10% del trabajo. El 90% está en la conversación y la confirmación. Sin conversación, la historia es solo papel muerto 📄.

🎮 Misión 2: Asigna cada elemento a su C (arrastra a la categoría correcta)

Puntos: 0/6

La estructura clásica de una historia de usuario sigue un patrón simple pero poderoso que captura tres elementos esenciales:

Fórmula: Como [rol], quiero [acción], para [beneficio]

👤 COMO [Rol]

¿Quién es el usuario que recibe valor? Especifica el rol o tipo de usuario.

Ej: "Como estudiante", "Como administrador", "Como cliente"

⚡ QUIERO [Acción]

¿Qué capacidad o acción necesita el usuario? Describe la funcionalidad.

Ej: "Quiero consultar mis notas", "Quiero generar reportes"

🎁 PARA [Beneficio]

¿Qué resultado o beneficio espera obtener? Justifica el valor.

Ej: "Para planificar mi estudio", "Para tomar decisiones"

✨ Ejemplo completo

Como estudiante activo del programa, quiero consultar el estado de mi solicitud de certificado, para que pueda saber cuándo estará disponible para recogerlo y planificar mi tiempo.

Esta historia es clara, específica y justifica por qué es importante para el usuario.

🎮 Misión 3: Completa la estructura (arrastra los elementos)

Puntos: 0/4

No todas las historias de usuario son buenas. Bill Wake creó el acrónimo INVEST como lista de comprobación para evaluar la calidad de una historia. Una buena historia debe cumplir estos seis criterios:

I - INDEPENDIENTE

La historia debe ser autosuficiente. No debería depender de otras historias para completarse.

Permite trabajo paralelo y priorización flexible.

N - NEGOCIABLE

No es un contrato fijo. Los detalles pueden evolucionar a través de la conversación.

Deja espacio para la creatividad técnica y ajustes.

V - VALIOSA

Debe entregar valor claro para el usuario, cliente o negocio.

Si no hay beneficio claro, reconsidera la historia.

E - ESTIMABLE

El equipo debe poder estimar el esfuerzo necesario.

Requiere claridad suficiente pero no detalles exhaustivos.

S - PEQUEÑA

Debe completarse en un solo sprint (idealmente en pocos días).

Historias grandes son épicos que necesitan dividirse.

T - COMPROBABLE

Debe haber forma de verificar la finalización mediante pruebas.

Sin criterios de aceptación claros, no se puede entregar confiablemente.

📊 Estadística importante

Según estudios de Agile Alliance, las historias que cumplen INVEST tienen un 40% menos de retrabajo y un 35% más de satisfacción del cliente que las historias mal definidas.

🎮 Misión 4: Evalúa la historia (selecciona si cumple INVEST)

Puntos: 0/3

Los criterios de aceptación son las condiciones específicas que deben cumplirse para que una historia de usuario se considere completa. Convierten ideas vagas en requisitos verificables 🎯.

Elementos de un criterio verificable

📋 REGLA

Condición que debe cumplirse

📊 DATO

Valor o límite medible

👁️ RESULTADO

Comportamiento observable

⚠️ EXCEPCIÓN

Respuesta ante error o caso límite

🔍 EVIDENCIA

Prueba o registro esperado

✨ Ejemplo de criterio débil vs mejorado

Criterio débil Problema Criterio mejorado
"El sistema validará correctamente la solicitud." No indica reglas ni resultado. "La solicitud se registra solo si el estudiante está activo, selecciona un tipo de certificado y adjunta soporte cuando exista cobro."
"La consulta debe ser rápida." No hay medida ni condición. "El estado se muestra en máximo 2 segundos para el 95% de las consultas, con hasta 500 usuarios concurrentes."
"Se mostrará un error adecuado." No define evento ni mensaje. "Si el código no existe, el sistema informa 'Solicitud no encontrada' y no expone datos de otros estudiantes."

🎮 Misión 5: Mejora el criterio (selecciona la versión mejorada)

Puntos: 0/3

La lista de reglas es útil cuando las condiciones son directas y no requieren describir una secuencia compleja. Es el formato más simple y directo para criterios de aceptación.

✨ Ejemplo: Consulta de estado de solicitud

  • El estudiante autenticado solo puede consultar solicitudes asociadas a su identificación.
  • La consulta presenta número de radicado, tipo de certificado, fecha, estado vigente y última observación pública.
  • Los estados permitidos son: Radicada, En validación, Requiere ajuste, Aprobada, Rechazada y Entregada.
  • Si no existen solicitudes, se informa la situación y se ofrece la opción de iniciar una nueva.

💡 Cuándo usar lista de reglas

  • Cuando las condiciones son independientes entre sí
  • Cuando no hay dependencias de estado complejas
  • Cuando necesitas especificar validaciones de datos
  • Cuando las reglas de negocio son directas

🎮 Misión 6: Identifica el formato (lista de reglas o Dado-Cuando-Entonces)

Puntos: 0/3

El formato Dado-Cuando-Entonces (Given-When-Then en inglés) representa ejemplos concretos de comportamiento. Es especialmente útil cuando el comportamiento depende del estado o contexto previo.

📌 DADO (Given)

Contexto y precondiciones. ¿Qué estado tiene el sistema antes?

Ej: "Dado que el estudiante tiene una solicitud en estado 'Aprobada'"

⚡ CUANDO (When)

Evento o acción ejecutada. ¿Qué hace el usuario?

Ej: "Cuando el estudiante consulta el estado de su solicitud"

✅ ENTONCES (Then)

Resultado observable esperado. ¿Qué debería pasar?

Ej: "Entonces el sistema muestra el estado 'Aprobada' y la fecha de entrega"

✨ Ejemplo completo

Dado que el estudiante Juan Pérez tiene una solicitud de certificado de estudios en estado "En validación"

Cuando el administrador aprueba la solicitud

Entonces el estado cambia a "Aprobada", se envía una notificación al estudiante y se genera un código de retiro

💡 Ventajas de GWT

  • Facilita la comunicación entre equipos técnicos y de negocio
  • Sirve como base para pruebas automatizadas (BDD)
  • Reduce ambigüedades al especificar comportamiento concreto
  • Es fácil de entender para no técnicos

🎮 Misión 7: Construye el escenario (arrastra los elementos)

Puntos: 0/4

Las historias de usuario no se escriben en aislamiento. La revisión colaborativa es fundamental para asegurar calidad. Diferentes roles aportan perspectivas únicas:

👤 ANALISTA

Explica necesidad y trazabilidad. Asegura que la historia esté alineada con objetivos del negocio.

🎭 USUARIO

Confirma valor y lenguaje del dominio. Valida que la historia realmente resuelve su problema.

💻 DESARROLLO

Valida factibilidad técnica y estimación. Identifica dependencias y riesgos técnicos.

🧪 PRUEBAS

Verifica verificabilidad y cobertura. Asegura que los criterios puedan probarse efectivamente.

🎯 Objetivo de la revisión

La revisión colaborativa asegura que cada historia sea: clara para todos, técnicamente viable, valiosa para el usuario y verificable mediante pruebas. Es un filtro de calidad antes de que la historia entre al sprint.

🎮 Misión 8: Identifica el rol (selecciona quién aporta cada perspectiva)

Puntos: 0/4

La trazabilidad es la capacidad de rastrear el origen y el destino de cada requerimiento. La cadena mínima de trazabilidad conecta los elementos clave del proyecto:

OBJETIVO

Plan/Problema

→
NECESIDAD

Oportunidad

→
HISTORIA

Capacidad con valor

→
CRITERIO

Condición de aceptación

→
PRUEBA

Evidencia de cumplimiento

💡 Beneficios de la trazabilidad

  • Permite saber el origen de cada requerimiento (por qué existe)
  • Facilita el impacto de cambios (qué afecta si cambiamos algo)
  • Asegura que no se pierdan requisitos en el proceso
  • Soporta auditoría y cumplimiento
  • Mejora la comunicación entre equipos
