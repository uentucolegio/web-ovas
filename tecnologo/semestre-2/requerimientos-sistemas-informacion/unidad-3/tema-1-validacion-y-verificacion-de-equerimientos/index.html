🚀 Validación y Verificación de Requerimientos: El Arte de Construir el Software Correcto

¡Hola! 👋 Imagina esta escena: trabajas durante semanas en una genial aplicación móvil para pedir comida a domicilio. Diseñas pantallas hermosas, la base de datos es rápida y la app se ejecuta sin un solo error de código. ¡Es una obra maestra técnica! 🍕📱 Sin embargo, cuando la lanzas en las tiendas de apps, descubres que los usuarios querían hacer pedidos grupales dividiendo la cuenta entre amigos, ¡pero tu app solo permite pedidos individuales!

¿Qué salió mal? 🤯 Tu código funcionaba perfectamente, pero resolvía el problema equivocado. Un requerimiento puede estar escrito sin errores sintácticos y aun así describir algo que nadie necesita. Por el contrario, una gran necesidad real puede perderse por culpa de una redacción ambigua o contradictoria.

🔍 El Puente del Éxito en Software

Un requerimiento listo para producción debe ser claro para todo el equipo (desarrolladores, diseñadores, testers y usuarios). Para asegurarlo, la norma ISO/IEC/IEEE 29148 define 8 criterios clave de calidad. 📜

Figura 4. Criterios principales de calidad de un requerimiento. Fuente: Elaboración propia (2026).

1. Necesario 📌

¿Responde a un objetivo real? Defecto: Pedir una función que ningún usuario utiliza.

2. Claro y Sin Ambigüedad 🎯

¿Tiene una sola interpretación? Defecto: Usar "El sistema será rápido".

3. Completo 🧩

¿Incluye condiciones, datos y reglas? Defecto: Omitir qué pasa si el pago falla.

4. Consistente ⚖️

¿Coincide con otros requisitos? Defecto: Un requisito permite editar y otro lo prohíbe.

5. Factible 🛠️

¿Puede lograrse con las restricciones? Defecto: Exigir consultar una API externa sin acceso.

6. Verificable 🧪

¿Se puede diseñar una prueba objetiva? Defecto: "La interfaz será muy agradable".

7. Trazable 🔗

¿Se relaciona con su origen y pruebas? Defecto: No tener ID ni vínculo con una necesidad.

8. Priorizado 🥇

¿Su importancia está acordada? Defecto: Marcar todo como obligatorio sin análisis.

⚡ Ejemplo de Transformación de Requerimiento

❌ Requerimiento Débil:

"El sistema debe mostrar rápidamente el estado del certificado."

Defectos: "rápidamente" es ambiguo, no indica actor, datos visibles ni métrica de rendimiento.

✅ Requerimiento Mejorado & Verificable:

"Cuando un estudiante autenticado consulte una solicitud propia, el sistema mostrará el número de radicado, el tipo de certificado, la fecha, el estado vigente y la última observación pública en máximo dos segundos para el 95 % de las consultas bajo la carga definida para pruebas."

Virtud: Precisa actor, condición, datos explícitos, métrica exacta y ámbito de prueba.

Existen distintas formas de verificar los documentos de requerimientos según el nivel de rigurosidad y el riesgo del proyecto. 🧐

Figura 5. Técnicas de verificación según el nivel de rigurosidad. Fuente: Elaboración propia (2026).

3.3.1 Revisión Individual con Lista de Chequeo

El analista revisa su propio documento usando una guía predefinida para eliminar palabras vagas y datos faltantes antes de publicarlo.

3.3.2 Revisión por Pares (Peer Review)

Un compañero de equipo examina la especificación desde otra perspectiva para descubrir supuestos o sesgos del autor original.

3.3.3 Recorrido Estructurado (Walkthrough)

El autor expone el requerimiento paso a paso ante desarrolladores y testers para evaluar flujos, reglas y excepciones.

3.3.4 Inspección Formal

El método más riguroso. Incluye roles definidos (moderador, lector, inspector), lista oficial de hallazgos y verificación de correcciones.

🛠️ Matriz de Diagnóstico y Corrección de Defectos

Defecto Encontrado Efecto Posible Acción de Corrección
Uso de "rápido", "adecuado", "fácil" No se puede construir una prueba objetiva en QA. Definir medida exacta, condición y umbral de tiempo.
Regla de negocio incompleta El sistema producirá comportamientos erráticos o impredecibles. Precisar condiciones, excepciones y resultados esperados.
Dos requerimientos contradictorios El equipo técnico no sabrá cuál regla programar. Consultar la fuente autorizada y registrar la decisión final.
Requerimiento sin origen (huérfano) No se justifica su desarrollo ni el costo de mantenerlo. Vincularlo formalmente con la necesidad, actor u objetivo.

❓ Guía de Preguntas Útiles durante la Validación

Antes de la tarea: "¿Qué debe haber ocurrido antes y qué información previa necesita para iniciar?"
Durante la tarea: "¿Qué decisiones toma el usuario en este paso y qué reglas aplica?"
Resultado esperado: "¿Qué comprobación o documento le confirma que el proceso terminó con éxito?"
Situación alterna / error: "¿Qué ocurre si la solicitud pertenece a otra persona o el sistema no responde?"

La Verificación y la Validación se ejecutan de forma iterativa en un circuito continuo de calidad. 🔄

Figura 7. Ruta integrada de revisión y trazabilidad. Fuente: IA (2026).

  1. Preparación: Definir alcance, versión del documento y evidencias.
  2. Verificación interna: Revisar sintaxis, completitud y factibilidad.
  3. Corrección inicial: Eliminar defectos de redacción antes de llamar al cliente.
  4. Validación con usuarios: Presentar escenarios, prototipos y reglas.
  5. Registro de decisiones: Clasificar observaciones (Aceptado, Rechazado, Pendiente).
  6. Actualización y trazabilidad: Modificar los requerimientos y sus pruebas asociadas.
  7. Confirmación de cierre: Comprobar correcciones y obtener la firma de aprobación.

📌 Caso Práctico Resuelto: Solicitud de Certificados (REQ-07)

1. Requerimiento Inicial (Débil):

REQ-07. El sistema permitirá consultar fácilmente el estado de los certificados y notificará cualquier novedad.

2. Hallazgos de Verificación:

"Fácilmente" no es medible; no especifica quién puede consultar; omite reglas de privacidad y datos visibles.

3. Requerimiento Validado (Final):

REQ-07. Cuando un estudiante autenticado consulte una solicitud asociada a su identificación, el sistema mostrará número de radicado, tipo de certificado, fecha de solicitud, estado vigente y última observación pública. Si el radicado no pertenece al estudiante, el sistema no mostrará información y registrará el intento de consulta.
