Casos de Uso UML

Imagina que estás diseñando una app para pedir comida 🍔. ¿Cómo le explicas al equipo de desarrollo qué debe hacer la app? ¿Cómo sabes si has pensado en todas las funcionalidades que los usuarios necesitan? ¡Aquí es donde entran los casos de uso UML!

Los casos de uso son como mini-historias que describen cómo interactúan los usuarios con el sistema. No son código, son diagramas visuales que cualquiera puede entender, desde el cliente hasta el programador. Son el puente entre lo que la gente quiere y lo que el software hace 🌉.

Según la Object Management Group (OMG), UML es el estándar mundial para modelar sistemas, y los casos de uso son una de sus partes más usadas. De hecho, el 85% de los proyectos de desarrollo de software utilizan UML en alguna etapa del proceso. ¡Es como el idioma universal del software! 🌍

✨ En este OVA aprenderás a leer y crear diagramas de casos de uso, entender las relaciones «include» y «extend», y evitar los errores más comunes. ¡Prepárate para dibujar como un profesional! 🎨

Objetivos de aprendizaje

  • 🎯 Comprender la notación esencial de casos de uso UML: sistema, actor, asociación, generalización, «include» y «extend».
  • 📐 Identificar y nombrar correctamente los casos de uso usando el formato verbo + objeto, enfocándose en el objetivo del actor.
  • 🔗 Diferenciar y aplicar correctamente las relaciones «include» y «extend», entendiendo su dirección y significado.
  • ⚠️ Reconocer y corregir errores comunes en diagramas de casos de uso: nombres incorrectos, uso indebido de relaciones, falta de especificación textual.
  • 🎨 Crear diagramas de casos de uso claros y completos que representen adecuadamente las funcionalidades de un sistema.

Un diagrama de casos de uso muestra las interacciones entre los usuarios (actores) y el sistema. Los elementos principales son:

👤 Actor

Representa un rol que interactúa con el sistema. Se dibuja como una figura de palo (stick figure).

⭕ Caso de uso

Representa una funcionalidad o servicio que el sistema proporciona a los actores. Se dibuja como un óvalo.

📦 Sistema

Representa el límite del sistema. Se dibuja como un rectángulo que contiene los casos de uso.

➖ Asociación

Representa la comunicación entre un actor y un caso de uso. Se dibuja como una línea sólida.

💡 Regla de oro

Nombra los casos de uso con verbo + objeto (ej: "Consultar saldo", "Registrar usuario"). Esto enfoca el caso de uso en el objetivo del actor, no en la implementación técnica.

Las relaciones permiten reutilizar y organizar casos de uso. Las dos más importantes son:

«include» (inclusión)

Cuándo usar: Cuando un caso de uso siempre incluye el comportamiento de otro.

Dirección: La flecha apunta del caso base al caso incluido.

Ejemplo: "Pagar factura" «include» "Consultar saldo" (siempre se consulta el saldo antes de pagar).

«extend» (extensión)

Cuándo usar: Cuando un caso de uso opcionalmente extiende el comportamiento de otro bajo ciertas condiciones.

Dirección: La flecha apunta del caso extendido al caso base.

Ejemplo: "Imprimir recibo" «extend» "Pagar factura" (opcionalmente se imprime el recibo después de pagar).

⚠️ Consejo de expertos

Martin Fowler sugiere usar «extend» con moderación por su complejidad. Prefiere «include» para comportamientos compartidos obligatorios. Menos es más en diagramas de casos de uso.

Evita estos errores frecuentes al crear diagramas de casos de uso:

❌ Nombres incorrectos

Error: Usar nombres técnicos o de implementación (ej: "CRUD usuarios", "Validar formulario").

Corrección: Usa verbo + objeto enfocado en el objetivo del actor (ej: "Gestionar usuarios", "Registrar datos").

❌ Uso indebido de relaciones

Error: Usar «extend» para comportamiento obligatorio o «include» para comportamiento opcional.

Corrección: «include» para obligatorio, «extend» para opcional/condicional. Verifica la dirección de las flechas.

❌ Falta de especificación textual

Error: Crear solo el diagrama sin documentar los casos de uso textualmente.

Corrección: Documenta cada caso de uso con: precondiciones, flujo principal, flujos alternativos y postcondiciones.

❌ Demasiadas relaciones

Error: Conectar todo con todo, creando un diagrama incomprensible.

Corrección: Mantén el nivel de abstracción y justifica cada relación. Menos es más.

La generalización de actores permite representar relaciones de herencia entre actores, similar a la herencia en programación orientada a objetos.

💡 ¿Cuándo usarla?

Cuando varios actores comparten los mismos casos de uso. El actor padre hereda todos los casos de uso de sus hijos.

✅ Ejemplo correcto

Padre: Usuario

Hijos: Administrador, Cliente, Empleado

Todos heredan los casos de uso comunes de "Usuario" (ej: "Iniciar sesión").

📐 Notación

Se dibuja con una línea sólida con una flecha triangular apuntando al actor padre (general).

La flecha indica "es un tipo de" (is-a relationship).

⚠️ Precaución

No abuses de la generalización. Úsala solo cuando realmente exista una relación "es un tipo de" significativa. Si los actores no comparten comportamiento significativo, es mejor mantenerlos separados.

El diagrama visual es solo el inicio. Cada caso de uso debe documentarse textualmente con detalle para que los desarrolladores puedan implementarlo correctamente.

📋 Plantilla de especificación textual

SECCIÓN DESCRIPCIÓN
Nombre Identificador único del caso de uso (ej: UC-01)
Actor principal Usuario que inicia el caso de uso
Precondiciones Estado del sistema antes de iniciar
Flujo principal Pasos normales del caso de uso
Flujos alternativos Variantes y excepciones
Postcondiciones Estado del sistema después de completar

✅ Beneficios

  • Claridad para el equipo de desarrollo
  • Base para casos de prueba
  • Documentación de requisitos verificables
  • Facilita la comunicación con stakeholders

Los casos de uso deben mantener un nivel de abstracción apropiado. Ni tan detallados que parezcan código, ni tan generales que no sirvan para nada.

❌ Nivel demasiado bajo

Ejemplo: "Hacer clic en botón", "Validar campo email", "Mostrar mensaje de error"

Problema: Son detalles de implementación, no objetivos del usuario.

✅ Nivel correcto

Ejemplo: "Registrar usuario", "Consultar saldo", "Generar reporte"

Ventaja: Representan objetivos significativos del usuario.

❌ Nivel demasiado alto

Ejemplo: "Gestionar sistema", "Usar aplicación"

Problema: Demasiado general para ser útil en el desarrollo.

💡 Regla de oro

Un caso de uso debe representar un objetivo completo y significativo para el actor, que pueda realizarse en una sola sesión de interacción con el sistema.

Es importante distinguir entre casos de uso reales (concretos) y abstractos (generales) para mantener un diagrama claro y organizado.

✅ Caso de uso real

Definición: Caso de uso que representa una interacción concreta y completa entre un actor y el sistema.

Ejemplo: "Pagar con tarjeta de crédito", "Pagar con PayPal", "Pagar en efectivo"

Característica: Puede ser iniciado directamente por un actor.

🔮 Caso de uso abstracto

Definición: Caso de uso que representa funcionalidad compartida o general, no iniciado directamente por actores.

Ejemplo: "Procesar pago" (incluido por los casos de pago específicos)

Característica: Se usa a través de relaciones «include» o generalización.

⚠️ Cuándo usar casos abstractos

Usa casos de uso abstractos cuando detectas funcionalidad compartida entre varios casos de uso. Esto evita duplicación y facilita el mantenimiento del diagrama.

Actividad 3: Aplica las relaciones «include» y «extend»

Para el siguiente escenario, determina qué relación usar:

Escenario: Sistema de compras online

  • Al "Realizar compra", siempre se debe "Verificar stock" del producto.
  • Opcionalmente, después de "Realizar compra", se puede "Enviar factura por email" si el cliente lo solicita.

Respuesta:

  • "Realizar compra" «include» "Verificar stock" (obligatorio)
  • "Enviar factura por email" «extend» "Realizar compra" (opcional)
